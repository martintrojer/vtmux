# vtmux

**tmux on a modern stack: all the baggage, fast and lean, fewer paper cuts, better rendering.**

A drop-in replacement for tmux 3.8, written in Rust on [libghostty-vt](https://github.com/ghostty-org/ghostty). Same CLI, config, formats, hooks and control mode, so your `.tmux.conf`, plugins and scripts work unchanged.

- **All the baggage.** The quirks plugins and scripts depend on are kept, byte for byte. Not a re-imagining: if you want a new multiplexer model, use Zellij. vtmux is for keeping your tmux setup and putting a better core under it.
- **Fast and lean.** That's the goal, and it's measured, not assumed: big scrollback settles at a sixth to a third of tmux's memory, pane output costs under half of tmux's CPU, and a bare server or an idle pane uses a few MB more than tmux's (speed over a few MB, as Ghostty does). The comparison with tmux 3.8 is in [docs/PERFORMANCE.md](docs/PERFORMANCE.md).
- **Fewer paper cuts.** Long-standing tmux annoyances fixed without breaking compliance: each fix is opt-in or invisible to scripts ([docs/PAPERCUTS.md](docs/PAPERCUTS.md)). The first two make the active pane obvious, both opt-in: a focus ring instead of tmux's half-coloured border, and a pane blend that dims the other panes the way Ghostty dims unfocused splits. Real tmux bugs (data loss, hangs) are fixed by default and documented in [compat/DIVERGENCES.md](compat/DIVERGENCES.md).
- **Better rendering.** The server composites one frame per client and sends only what changed, inside synchronized output, with the cursor placed once, so heavy output doesn't make the cursor jump around ([how it works](docs/ARCHITECTURE.md)).

Just the core: no agent integration, no extra TUI, no animations. Images pass through to your terminal.

Compliance is checked against tmux's own regress suite and a behaviour oracle recorded from real tmux 3.8. Inside, it's idiomatic Rust: `unsafe` only at the FFI and OS boundary.

**Status:** early, not a daily tmux yet. M0 (the walking skeleton) is done; M1 (daily use) is well along. Working today: sessions, windows, panes and layouts, attach/detach, control mode (`-C`), options, formats, key bindings, hooks, the status line and messages, the command prompt, copy mode (search, selection, copy-pipe), `choose-tree` with its preview, clock mode, `display-panes`, paste buffers, popups, `run-shell`/`if-shell`, `#()` in formats, `%if` in configs, `set-titles`, `synchronize-panes`, the focus ring, and the mouse (clicks, the status line, the wheel, drag-select and border resize, forwarding to mouse-aware programs). Still missing: the other choose modes, menus. It passes all 265 behaviour-oracle scenarios recorded from real tmux 3.8 and 158 of tmux's 174 regress tests (12 are expected failures, each recorded in compat/expected.toml, and one is skipped). See the [spec](docs/specs/2026-10-29-vtmux.md) and [how it works](docs/ARCHITECTURE.md).

**Big scrollback is the lean story** (vs tmux 3.8, release build, Linux, a 96-cpu devserver at load 2.6-4.9; [numbers and method](docs/PERFORMANCE.md)): one pane with 1,000,000 lines of scrollback settles at 103 MB against tmux's 622 MB, one with 100,000 lines at 19 MB against 66 MB, and a session of 10 panes with 100,000 log lines each at 100 MB against 629 MB; a pane that keeps streaming at its 100,000-line limit stays at 19 MB. Until the idle history is compressed (about 15 s after 100,000 lines, 70 s after 1,000,000) vtmux holds up to 1.6x tmux's memory, and a search through all of it in copy mode is 3.4-5.0x slower (8 s against 1.7 s on 1,000,000 lines; entering copy mode is faster, 57 ms against 220 ms). Elsewhere: an idle server uses 9.0 MB against 4.2 MB and an idle pane 18 KB against 5.4 KB. Consuming 100 MB of pane output with no client takes 0.89 s of server CPU against 2.38 s (plain text); with a 200x50 client attached a flood takes 0.4-0.6x of tmux's server CPU, and with 8 clients 0.06-0.19x; a key's echo takes 0.33 ms against 0.21 ms (0.49 against 0.52 ms next to a flood). Many synthetic agent TUIs currently cost about 5x tmux's server CPU, a regression since hidden panes drop their screen views (see *Agent panes* there). With the owner's config (TPM plugins and the mu-crew poller) the idle server uses 9.7 MB against 4.6 MB and 47 ms of CPU a minute against 171 ms; sourcing the config takes about 100 ms for both.

Linux first, macOS second: CI runs the full gate, including the tmux comparison suites, on both. ISC license.
