# Divergences from tmux 3.8

vtmux follows tmux 3.8 exactly except where recorded here (spec: *Divergence
process*). Every entry needs evidence. There is no "intentional divergence for
product reasons" category. Protocol extensions (spec D28) have a category of
their own, below.

## Categories

- **Ghostty grid**: the D4 arbiter ruled for Ghostty's terminal-emulation behaviour over tmux's.
- **Do not copy tmux bug**: tmux loses data, hangs or is unsafe. Needs evidence and a regression test.
- **Deferred**: not done yet. Must not be claimed as compatible.
- **Spec decision**: a numbered decision in the spec (`docs/specs/2026-10-29-vtmux.md`) chose this behaviour for drop-in use. Cite the decision.
- **Extension (D28)**: a terminal protocol tmux 3.8 drops, which the pinned libghostty-vt implements in panes and Ghostty as the outer terminal (spec *Protocol extensions*). Only a program that asks through the protocol sees it, and only with its `vtmux-*` option on. Name the decision (D29, D30, D31, ...), the option, the oracle scenario that pins tmux's behaviour with the option off, the test that pins vtmux's with it on, and what a live upgrade keeps.

## Entry template

```
### D-NNN: <short title>

- Test / assertion: <regress test or oracle scenario, and the failing line>
- tmux behaviour: <what tmux 3.8 does>
- vtmux behaviour: <what vtmux does>

- Patch: <compat/patches/NNNN-name.patch, if the regress assertion is patched>
```

### D-001: `#{history_bytes}` and `#{history_all_bytes}` are a model of tmux's grid memory

- Test / assertion: oracle `history_bytes` (empty, scrolled, extended-cell and cursor-addressed panes) and the default-template `list-panes` step of `panes_split_resize` (`[history 0/2000, 120 bytes]`) match the reference; cli.rs compares `list-panes` with `-F` elsewhere. Oracle `history_bytes_resize` pins the width-change rows below: the rows that agree against the reference, the four that differ as `divergence` annotations.
- tmux behaviour: `format_cb_history_bytes` (format.c:996-1020) sums tmux's own grid memory: each line's `cellsize * sizeof(struct grid_cell_entry)` (5 bytes) plus `extdsize * sizeof(struct grid_extd_entry)` (23) plus `sizeof(struct grid_line)` (40) per line. A line's `cellsize` is what `grid_expand_line` (grid.c:564-589) allocated over its life: a quarter, a half or the whole width, for the furthest cell a write reached.
- vtmux behaviour: the grid is Ghostty's (D4), which has no per-line allocation, so `vtmux_vt::history_bytes` rebuilds the sum from the rows read back: 40 bytes a line, `cellsize` by the capture's allocation model (`tmux_cellsize`: one `grid_expand_line` per run of same-style ASCII text and one per cell tmux writes alone, D-027), and one extended entry for each cell `grid_need_extended_cell` (grid.c:117-138) would keep one for (a wide or non-ASCII character, an RGB or theme colour, an attribute past the first eight, an underline colour, a link, a tab's first cell). It is exact for lines that were written once at the width the pane has now: plain, wide, accented, RGB, tab and cursor-addressed text, empty rows, scrolled history, `clear-history`. `#{history_all_bytes}` (format.c:1022-1047: lines, their bytes, cell entries, their bytes, extended entries, their bytes) gives the same model's counts (oracle `format_history_all_bytes`). It differs for a line whose allocation is not what its cells alone give:
  - a line edited after it was written (erase to end of line, delete or insert characters, a shortened line): tmux keeps the allocation the longer text made, Ghostty keeps no such mark, so vtmux counts what is left;
  - any line after a width change (`resize-window`, a split, a client of another size, a window that follows it): `grid_reflow` (grid.c:1528-1600) moves a line that fits with its `celldata` and `cellsize` as they were (`grid_reflow_move`), keeps the first part of a split line at `at` cells (`grid_reflow_split`) and the first line of a join at its old size, and only the lines it fills afresh grow by `grid_expand_line` for the new width (a quarter, a half or all of it). A line first written at 80 columns holds 20 cells in tmux (a quarter) whatever the width becomes; vtmux counts it at the new width, 7 cells at 30 columns and 30 at 120; the counts agree only when both land on the same step. A model needs a per-line high-water mark of the allocated width that follows the line through Ghostty's reflow (a new `Row` field in the patched Ghostty, its state export and the snapshot format, and the split and join rules above); nothing known depends on `#{history_bytes}` being exact after a resize, so it is not built.
- Evidence: oracle `history_bytes` (traces from the reference); probes of `\033[K`, `\033[P` and `\033[@` after text on 40x6 give 340/440/440 bytes on the reference and 290/290/290 on vtmux. Oracle `history_bytes_resize`, 80x24 and 200 lines in the history (177 in it, 24 on the screen), tmux / vtmux: `1`..`200` one per line, 80 -> 30 columns 28040 / 15040, then 120 columns 28040 / 38040, back to 80 28040 / 28040, `split-window -h` (40 columns) 28040 / 18040; 53-character lines, 80 -> 30 76040 / 76040, 120 68040 / 68040, back to 80 68040 / 88040.
- Category: Deferred (the edited-line allocation and the allocation across a width change; nothing known depends on either).

### D-002: ERE resource limits (`m/r`, `s///`)

- Test / assertion: `crates/vtmux-core/src/regex/tests.rs` `regex_resource_limits_are_errors_not_panics`; `crates/vtmux-core/src/format/matching.rs` `format_matching_limit_is_regexec_failure`.
- tmux behaviour: glibc `regcomp`/`regexec` (format.c:format_match, regsub.c:regsub) have no step cap. Backreference searches backtrack without bound: `(a*)\1b` against 3000 `a` takes 47 s. Compiling fails with `REG_ESPACE` only when memory runs out.
- vtmux behaviour: patterns without backreferences have no work cap; they run in O(text × compiled nodes) (`regex/nfa.rs`). These limits remain and return `Error::Limit`: 64 nested groups or chained quantifiers, 128 groups plus quantifiers, about one million compiled nodes after `{m,n}` expansion (`(a{1000}){1000}` is refused; glibc compiles it), and for backreference patterns a backtracking budget of one million capture-weighted steps per start position (no cross-start ceiling, so an ordinary backreference on long text still finds its match). Backreference search is quadratic in text length: `(\w+) \1` on 1.9k chars takes about 1 s in a release build where glibc takes about 10 ms. The format layer handles a limit the way tmux handles a failed `regexec`: `m/r` gives `0`, and `s///` copies the rest of the text unchanged, keeping earlier replacements. A large `{m,n}` makes matching slow but still correct: `a{32767}` against 32767 `a` takes about 4 s (glibc: 0.07 s).
- Evidence: reviewer-8's `high_regex_work_budget_silently_turns` repros (`[0-9]+%` on 710 digits, `[a-z]+:`, `\w+@`, `[^ ]+ x` on 1000 chars, `(a|b)*c`, `.*z|q`) now match glibc 2.43 and the reference tmux 3.8 (`regex_long_texts_match_like_glibc`). 100k-character texts take < 1 s per search (`regex_without_backreferences_is_linear`). `(a*)\1b` against 3000 `a` gives `Limit` after about 1 ms, where glibc returns no match after 47 s.
- Category: Deferred

### D-003: glibc's `^` inside a repeated group

- Test / assertion: none fails (the rows below are not in `src/regex/golden.in`); task `regex_corners` probes against glibc 2.34 and 2.43 (python ctypes `regcomp`/`regexec`, as `tests/regex_cases.sh`) and reference tmux 3.8. The other corners this entry used to list now match and are pinned: an escaped lowercase letter under `REG_ICASE` (`\a`) never matches and the last iteration of an empty-matching repeat is reported (`(a*){2}` on `aa`: `\1` = 2:2) in `golden.in`; fnmatch `[a-[:digit:]]` fails the bracket in `fnmatch_golden.in`; the `s///` empty-match step of one byte in `format/matching.rs` `empty_matches_step_one_byte_as_regsub_does`.
- tmux behaviour: glibc's DFA ignores a `^` that is not at the start in a later iteration of a repeated group, and its answer depends on how many captures the caller asks for (regexec.c `re_search_internal`: only with `nmatch > 1` does `prune_impossible_nodes` check the span, and when that fails no shorter match is tried). `(^a|b)+` on `ba`: 0..2 with `nmatch` 1 (copy-mode search), a match with `nmatch` 0 (`m/r`), no match with `nmatch` 10 (`s///`: `#{s/(^a|b)+/X/:abab}` is `abab`). `(^a)+` on `aa` and `(a|^b)+` on `ab` behave the same. A backreference to such a group differs too: `(a*){2}\1` on `aa` is no match.
- vtmux behaviour: POSIX: `^` matches only at the start of the text in every iteration. `(^a|b)+` on `ba` is 0..1 whatever the caller asks for, and `#{s/(^a|b)+/X/:abab}` is `XX`; `(a*){2}\1` on `aa` matches 0..2.
- Evidence: task regex_corners probes (glibc 2.34 on CentOS 9, the same answers as 2.43 in review_fmt_regex); reference tmux 3.8 `display -p '#{m/r:(^a|b)+,abab} #{s/(^a|b)+/X/:#{l:abab}}'` gives `1 abab`, vtmux `1 XX`.
- Category: Do not copy tmux bug (a glibc DFA bug whose result changes with the number of captures requested; copying it means modelling glibc's DFA and its pruning).

### D-004: time formatting: C locale, long strftime output, TZ values glibc half-parses

- Test / assertion: `crates/vtmux-core/tests/time_cases.sh` (rows citing D-004); cli `format_time_out_of_range`, `format_time_unparseable_tz_name`; hand probes from review_fmt_time (reviewer-14).
- tmux behaviour: tmux calls `setlocale(LC_TIME, "")` and glibc `strftime`/`localtime_r` (format.c:4694-4700, 6728-6741). (1) A non-C `LANG` changes `%c %x %r %p %a %b`: `LANG=en_GB.UTF-8` gives `Fri 30 Oct 2026 14:32:28 GMT` for `%c`; `LANG=de_DE.UTF-8` gives `Do Okt` for `%a %b`. (3) `t/f` output longer than 511 bytes makes `strftime` fail and tmux prints its half-written stack buffer (`#{t/f/%H<600 y>:@n}` gives `16yyyy...`, as far as the buffer got). (4) A `TZ` that is neither a zoneinfo file nor a POSIX rule keeps its leading letters as the abbreviation (`__tzset_parse_tz`, time/tzset.c): `TZ=Invalid/Zone` gives `%Z` = `Invalid` with offset `+0000`, `TZ=AB/x` an empty `%Z`, `TZ=<+03>/x` gives `+03`. When a valid name and offset come first and garbage after, glibc keeps part of the rule: `EST5/x` is empty with `+0000`, `EST5EDT/x` is `EDT -0400`, `EST25` is `EST -2400`, `ABC-3abc,x` is `abc +0400`.
- vtmux behaviour: (1) C locale always (`Fri Oct 30 14:32:28 2026`, `Thu Oct`); `#{t:}` (ctime) is C in both. (3) output over 511 bytes is empty. (4) the cases with no offset after the name are as glibc's (`SystemWallClock::local_time`, `unparsed_tz_name`); a name followed by an offset that jiff rejects (the `EST5/x` family) is UTC with `%Z` `UTC`.
- Closed: years past 9999 format normally (`@big=999999999999` gives `33658 Fri`, `Tm::in_zone`; cli `format_time_out_of_range`, golden rows at 99999999999).
- Why (1) and the rest of (4) stay: (1) needs the C library's locale data. The core crates forbid `unsafe` (D10), so the answer would come through a hook from `sys/` into libc `setlocale`/`strftime`; which locales exist differs per host (this one has `en_GB` and `en_US`, no `de_DE`), so a test either skips (a skip is not a pass) or needs a locale CI may lack, and on macOS the libc is Darwin's, not glibc's. The `EST5/x` family needs a model of what glibc's POSIX parser keeps of a half-valid rule (names, offsets and default DST rules). (3) prints uninitialised stack bytes after the part strftime wrote, so there is nothing stable to copy.
- Evidence: reference tmux 3.8 and glibc 2.34: probes of 24 `TZ` values and `LANG=en_GB.utf8`/`en_US.utf8` in the task `div_smalls_b` (cli test `format_time_unparseable_tz_name` compares eleven of them on Linux); reviewer-14's probes on b6b2721.
- Category: Deferred (1, and the offset-then-garbage cases of 4); Do not copy tmux bug (3, a print of uninitialised memory).

### D-005: a loop nested in a loop of the same kind does not disturb the outer order

- Test / assertion: `crates/vtmux-core/tests/loop_cases.sh`, the row citing D-005 (`#{S:#{S/n:#{session_name}}-#{session_name} }`).
- tmux behaviour: `sort_get_sessions`, `sort_get_winlinks_session`, `sort_get_panes_window` and `sort_get_clients` (sort.c:461-600) return one static array per kind, which every call refills and sorts in place. A nested loop of the same kind therefore re-sorts the array the outer loop is walking, and the outer loop reads the inner order from then on. With sessions zeta, alpha, mike (IDs 0, 1, 2) the outer loop visits zeta, then reads index 1 and 2 of the name-sorted array: `alphamikezeta-zeta alphamikezeta-mike alphamikezeta-zeta`, so mike is visited once, zeta twice and alpha never.
- vtmux behaviour: each loop sorts its own list; the outer loop visits each session once in its own order: `alphamikezeta-zeta alphamikezeta-alpha alphamikezeta-mike`.
- Evidence: reference tmux 3.8, the `loop_cases.sh` topology (reference value kept in the row's comment).
- Category: Do not copy tmux bug (the outer loop skips and repeats items; copying it means sharing a mutable list across nested expansions).

### D-006: a pane without history keeps none of the lines a narrowing pushes off its top

- Test / assertion: none fails. The wrap-flag bookkeeping is pinned by oracle `wrap_flag_capture_join` (29 scenes: EL, ED, IL, DL, SD, SU, RI, regions, the history row, the alternate screen), `wrap_flag_redraw_copy` (the redraw of a blank run and copy mode's `select-line`), `wrap_flag_resize` (15 scenes of moves then a wider pane) and `reflow_cells_used` (patches 0011-0013), and its corners by `wrap_flag_corners` (patch 0029).
- tmux behaviour: `grid_reflow` (grid.c) sets `hsize` to the lines a narrowing adds above the screen whether or not the grid has `GRID_HISTORY`, so a pane made with `history-limit` 0 has history after it narrows (nothing collects it, `grid_collect_history` runs only for `GRID_HISTORY`), and widening joins those lines back onto the screen.
- vtmux behaviour: a pane without history has no Ghostty scrollback (bytes 0, the no-scrollback paths tmux's missing `GRID_HISTORY` also takes), so the rows a narrowing pushes up are dropped: `#{history_size}` stays 0, and widening brings nothing back. The corners this entry listed before match since patch 0029: EL 2 on a line never written to (`cellsize` 0) in the default background unwraps nothing (`screen_write_clearline` returns early); scroll-on-clear scrolls the lines up to the last with cells used, erased ones included (`grid_view_clear_history`); IL and DL with the cursor outside the scroll region work on the whole screen (`grid_view_insert_lines`, `grid_view_delete_lines`; an IL count reaching the bottom moves nothing); without history a region of two rows scrolled up unwraps the line moved to its top and one of one row (a one-row pane) does not scroll, and SD and RI do not scroll a one-row pane at all (`grid_move_lines` of `rlower - rupper` lines). Two related differences have their own entries: a line scrolled out of a region that does not start at the top (D-032) and the trailing erased cells `capture-pane -J` keeps on a wrapped line (D-027, the `cellsize` model).
- Evidence: reference tmux 3.8, `set -g history-limit 0`, `printf 'aaaaaaaaaa\r\nbbbbbbbbbb\r\ncc'` on 10x3, `resize-window -x 5`: tmux `#{history_size}` 2 and `capture-pane -p -S -` `aaaaa` / `aaaaa` / `bbbbb` / `bbbbb` / `cc`, then `-x 10` all three lines back; vtmux 0 and `bbbbb` / `bbbbb` / `cc`, then `bbbbbbbbbb` / `cc` / blank. The corners: task div_wrap_tab_reflow probe, 38 scenes against tmux 3.8 (EL, ED 2 under scroll-on-clear, LF, SU, SD, RI and regions on one- and two-row panes with and without history and on the alternate screen, IL and DL outside the region): 23 differed before patch 0029, and with it two do, a region scroll into history (D-032) and the trailing erased cells of a `-J` capture (D-027).
- Category: Deferred (a pane without history would need Ghostty scrollback that only a reflow fills and nothing else does).

### D-007: terminals come from a built-in table, and frames use fixed sequences

- Test / assertion: `crates/vtmux-core/src/term_features/golden.rs` (215 reference rows from `tests/term_features_cases.py`, 37 of them for the terminals and overrides below), `term_features` `table_tests`; `crates/vtmux/tests/attach.rs` `terminal_features_apply_at_attach`, `terminals_tmux_knows_attach`, `terminals_tmux_refuses_leave_no_session`, `terminfo_keys_follow_the_terminal`, `overrides_remove_the_alternate_screen`, `colours_below_256_are_downgraded_like_tmux` (`linux`, `vt100`), `cursor_style_and_colour_reach_the_terminal`, `application_escape_mode_follows_the_appesc_feature`, `the_console_cursor_is_hidden_with_civis`; `term_features` `code_tests`; `render` `attributes_follow_the_terminal`, `underline_styles_colours_and_overline_follow_the_terminal`; oracle `term_console_vt`, `attach_underline_styles`, `attach_attributes_by_terminal`.
- tmux behaviour: tmux's client reads the terminal's terminfo entry (`tty_term_read_list`, tty-term.c) and refuses a name the database lacks (`missing or unsuitable terminal: NAME`, client.c:325-331) for any command run from a terminal. `tty_term_create` applies `terminal-features` (tty-features.c), `COLORTERM`, then `terminal-overrides` (`tty_term_apply`) to any of ~250 capability names, refuses a terminal without `clear` or `cup`, and every sequence it writes is a terminfo string. Later device-attribute replies add features too (`tty_default_features`: `XTVERSION`, DA2).
- vtmux behaviour: vtmux reads no terminfo (D8). Its terminals are a table generated from terminfo by `tests/terminfo_table.py` (`terminfo.rs`): 70 names, the `xterm` family with `xterm-kitty` and `xterm-ghostty`/`ghostty`, `screen`, `screen-16color`, `screen-256color` and the 19 `screen.*` entries, `tmux`, `tmux-256color`, `tmux-direct`, `linux`, `linux-16color`, `rxvt*`, `alacritty*`, `kitty*`, `foot*`, `st*`, `vte*`, `gnome*`, `konsole*`, `putty*`, `iterm2`, `mintty`, `ms-terminal`, `vt100`, `vt102`, `vt220` and `dumb`; an `xterm*` name not in it takes `xterm`'s entry with the colours its name suggests. Each entry keeps the `tty_term_codes` names it has, which flags are false, `colors`, and the strings vtmux writes or decodes. Generated on CentOS 9 (ncurses 6.2 with ncurses-term, kitty's terminfo, and Ghostty's from the pinned ghostty commit's `src/terminfo/ghostty.zig`); the cursor (`civis` too), underline and standout strings were added on a CentOS 9 host without kitty's and Ghostty's entries or the newer ncurses ones, whose entries were carried over unchanged with those values from `ghostty.zig` (`ghostty`, `xterm-ghostty`) or the ncurses entry each is built on (`alacritty-direct`, `kitty-direct` and `xterm-kitty` from `kitty`, `konsole-direct`, `linux-16color`, `st-direct`, `vte-direct`); `foot` and `foot-direct` are not in ncurses 6.2, so they take `xterm-256color`'s and `xterm-direct`'s entries until the table is regenerated on a host that has them (foot's XTVERSION reply adds its features at runtime, as in tmux). A name outside the table is refused when its terminal is opened, with tmux's `missing or unsuitable terminal: NAME`; tmux refuses it in the client for every command, vtmux only for `attach` and `new`, and a name the host's terminfo has but the table lacks is refused where tmux attaches it; a name the table has but the host's terminfo lacks attaches where tmux refuses it (`TERM=xterm-ghostty` over SSH to a Linux host without Ghostty's terminfo: tmux `missing or unsuitable terminal: xterm-ghostty`, exit 1; vtmux attaches with Ghostty's entry, audit_owner_setup_linux). A terminal left without `clear` or `cup` after the overrides (`dumb`, an empty `TERM`, `cup@`) is refused with `open terminal failed: terminal does not support clear` as in tmux, before `new-session` makes the session. Feature parsing, `terminal-features` matching, `COLORTERM`, the `-T`/`-2` flags and `TERM_VT100LIKE` (`XT` or a `clear` that starts with CSI) follow tmux. What vtmux writes follows the entry and the overrides for: the start, stop and lock sequences (`smcup`, `rmcup`, `clear`, `smkx`, `rmkx`, `cnorm`, `E3`, `indn`/`ind`, and the mouse, bracketed-paste and focus modes only with `kmous`, `Enbp`/`Dsbp` and `Dsfcs`; so `smcup@:rmcup@` keeps the terminal on its normal screen), `bce` and `am`, colours (`colors`, also as an override, sets the palette and `#{client_colours}`; a terminal without `setaf`/`setab` gets no colours and a background as reverse video, `tty_attributes`), the key tree (`kf1`-`kf12`, `kich1`, `kdch1`, `khome`, `kend`, `knp`, `kpp`, `kcbt`: the console's `ESC [[A` is F1; `kf13`-`kf63` and the modified `kIC`, `kHOM`, `kUP3`... are not in it, so `linux`'s `ESC [25~` (its `kf13`, tmux's S-F1) is S-F3 by the rxvt rows and `rxvt`'s `ESC [2$` (`kIC`, tmux's S-IC) is M-[ and text), the title (`tsl`, `fsl`), `Ms`, `Eneks` and `Dseks`. Frames otherwise use fixed xterm sequences whatever the entry has: `cup`, `el`, `ech` (`vt100` has no `ech`), `csr`, `sgr0`, and the attributes' SGR codes, each written only when the terminal has its capability, as `tty_attributes` does (`bold`, `dim`, `sitm` else `smso`, and `smso` under a `screen` or `screen-*` `default-terminal`, `smul`, `blink`, `rev` else `smso`, `invis`, `smxx`, `Smol`, `Smulx`, `Setulc` and `Setulc1`), in xterm's form or the form tmux's own feature gives (`\E[4:Nm`, `\E[58:2:R:G:Bm`, `\E[58:5:Nm`, `\E[53m`), not the entry's template (Ghostty's `Setulc` is `\E[58:2::R:G:Bm`); `smso`'s SGR parameter comes from its string (screen's is 3). The startup queries also go to a terminal an override made not VT100-like (tmux sends none). The `margins` feature's `Enmg`/`Dsmg` are not written: vtmux never uses DECSLRM. The cursor (`cnorm`, `Ss`, `Se`, `cvvis`, `Cs`, `Cr`), bracketed paste (`Enbp`, `Dsbp`), focus (`Enfcs`, `Dsfcs`) and application escape (`Enesc`, `Dsesc`) strings are written from their values (the entry's, a feature's or an override's) through a `tparm` model; the table keeps the values of `civis` (a frame hides the cursor with it, and ends a hidden one with `cnorm` when it is more than DECTCEM, as on `linux`: `ESC[?25l ESC[?1c`; a terminal without `civis` gets none), `cvvis`, `smso`, `Ss`, `Se`, `Cs`, `Cr`, `Smulx`, `Setulc` and `Smol`, and a name it has without a value (`mintty`, `iterm2`, `ms-terminal`: not on the generating host) takes the value tmux's feature gives. For `Tc`, `RGB`, `setrgbf`, `setrgbb`, `Sync`, `Smulx` and `Setulc` frames go by the presence of the capability: `Sync=x` or `Sync=QQ%p1%dQQ` still gives `ESC[?2026h` where tmux writes the template (nothing at all for a value that does not expand to a sequence), and `setrgbf` is always `38;2;r;g;b` where Ghostty's terminfo makes tmux write `38:2:r:g:b`. `Ms` is validated with a model of `tty_term_validate`'s check, fitted to 40 probed templates. Every other name is tracked by presence (features add and `ignorefkeys` removes theirs, overrides set and remove them), so `#{I/c:name}` and `#{I/f:name}` answer as tmux does for the host the table was generated on. The startup queries are tmux's (DA, DA2, XTVERSION, DECRQM 2026, the OSC 10/11 colours, and `?996n` with `?2031h`), and their replies add features as tmux's do (`tty_keys_sync`, `tty_keys_device_attributes`, `tty_keys_device_attributes2`, `tty_keys_extended_device_attributes`); XTVERSION sets `#{client_termtype}`. Then `Eneks` and `Enfcs` are written as `tty_update_features` writes them, but the client is redrawn only if a capability vtmux draws with changed (tmux always redraws; the screen is the same). vtmux does not repeat the colour queries on a resize (`tty_repeat_requests` after `TTY_REQUEST_LIMIT`), only after a theme report, and a reply that arrives after its query was answered or timed out is swallowed where tmux reads it as keys. The `hyperlinks` feature is tracked and listed but the compositor does not yet write OSC 8 (tmux writes a pane's links as `\E]8;id=tmuxN;URI\E\\` to a terminal with `Hls`).
- Evidence: reference tmux 3.8 `list-clients -F '#{client_termfeatures}|#{client_colours}|#{Ic:...}'` on a PTY client for every row of `golden/cases.tsv`; `Ms` probes in `term_features_cases.py` rows `xterm*:Ms=...`; task div_terminals_overrides: the reference attaches `linux`, `alacritty`, `xterm-kitty`, `kitty`, `screen.xterm-256color`, `screen.linux`, `tmux`, `tmux-direct`, `rxvt`, `rxvt-unicode-256color`, `vt100`, `vt220`, `st-256color` and `putty-256color` with the features and colours vtmux now gives (vtmux refused them all), and refuses `dumb`, an empty `TERM` and `bogus` with the texts above (vtmux left the `new-session` session behind).
- Category: Deferred (terminals outside the table; frames written with fixed sequences)

### D-008: respawn-window -k on a zoomed window

- Test / assertion: `crates/vtmux/tests/cli.rs` `windows_respawn_zoomed` (vtmux only: the reference dies).

### D-029: a client whose socket takes nothing for 10 s after its exit is dropped then

- Test / assertion: regress `control-client-exit-stalled.sh`; control `stalled_client_does_not_keep_the_server`, `slow_reader_detached_in_a_flood_exits_cleanly`.

### D-068: a link's external id is numbered when it is first drawn

- Test / assertion: oracle `osc8_ids_numbered_when_drawn` (annotated, the three screens); `osc8_to_clients` and attach.rs `hyperlinks_*` match the reference where the order is the same.
- tmux behaviour: a link's external id (`tmuxN`, the `id=` a terminal with `Hls` is given, tty.c `tty_hyperlink`) comes from one counter for the server when the OSC 8 is parsed (input.c `input_osc_8`, hyperlinks.c `hyperlinks_put`): a link that scrolls into history before any client draws it still takes the next number. A `link=` style's URI takes one number in `style_hyperlinks` when the style is parsed and one more in each screen it is drawn on (format-draw.c `format_draw`): each client's status line, each pane's border line. At 5000 links in the server the oldest is forgotten, and its cells are drawn with no link.
- vtmux behaviour: the grid is Ghostty's (D4), which keeps each cell's URI and OSC 8 id but no number; vtmux gives a link its number the first time a cell of it is read for drawing (`vtmux_vt::link`), from one counter for the server. Links drawn in the order they were written (anything that fits the screen when drawn, copy mode over history nothing drew) get tmux's numbers; links that scrolled away undrawn are numbered after those on the screen. A `link=` URI takes two numbers the first time it is drawn anywhere and keeps the second for every client and line. Past 5000 links a pane forgets those no cell on screen holds, and a cell of one drawn again takes a new number. A live upgrade keeps each pane's numbers (`drawn_links` in the snapshot) and the counter (`link_number`, so a link drawn after it never takes a number still on screen); a copy mode restored from one keeps only URIs, so its links take the pane's link of that URI when it has one, else a new one; `link=` URIs are numbered again. Which cells are one link, their URIs and where links start and end are tmux's.
- Evidence: reference tmux 3.8, the scenario's trace: two links without an `id=` and one with one scroll into history before the attach, a fourth stays on the screen: tmux draws it as `tmux4` and copy mode the others as `tmux1`-`tmux3`; vtmux draws it as `tmux1`, the others as `tmux2`-`tmux4`.
- Category: Deferred (numbering at parse time needs Ghostty's implicit id for each OSC 8 as it is parsed: a Ghostty patch).
