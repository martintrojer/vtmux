# Paper cuts

Long-standing tmux usability defects that vtmux fixes without breaking compliance. The rules are in the spec, *Paper-cut fixes*: fix a defect in existing behaviour, keep compliance (opt-in, or invisible to scripts), cite the tmux source, and pin it with a test.

| Paper cut | tmux reference | vtmux fix | Option | Status |
|---|---|---|---|---|
| Active pane is hard to see: shared borders are half-coloured, arrows are one cell | `pane-border-indicators`, `screen-redraw.c` (`style_wp`, `redraw_mark_border_arrows`) | Focus ring: outer frame, active pane enclosed by heavy lines in the active colour | `vtmux-focus-ring` (D23) | removed 2026-11-06, superseded by pane blend (D26): the blend gives the active-pane cue at zero cell cost; the ring cost 2 columns and 2 rows per window and changed window and pane geometry against tmux while on. A config that still sets `vtmux-focus-ring` gets tmux's `invalid option` error (pinned by `vtmux_options_invisible_while_unset`) |
| Active pane is still easy to miss in a two-pane split, and the focus ring (removed 2026-11-06) cost a 1-cell frame | `pane-border-indicators`, `window-style`/`window-active-style` only reach default-colour cells (`tty_default_colours`), so TUIs that paint their own colours don't change; Ghostty's `unfocused-split-opacity` dims a whole split but never worked inside tmux | Pane blend: every cell of the inactive (or active) pane, explicit colours included, is blended toward a colour in the compositor, zero cells spent. `fg=bg/25,bg=bg/25` matches Ghostty's 0.75 opacity. Spec: `docs/specs/2026-11-04-pane-blend.md` | `vtmux-pane-active-blend`, `vtmux-pane-inactive-blend` | done (M1): `render/blend.rs`; OSC 10/11 at attach as tmux, plus OSC 4 0-15 (D-033); no reply, no blend; pinned by `pane_blend_*` (`crates/vtmux/tests/attach.rs`), `pane_blend_keeps_the_frame_skip`; `BLEND=1 scripts/bench.py render throughput_attached` server CPU within 3% of off ([numbers](test-health/2026-11-04-pane-blend-bench.md)) |
| Cursor flickers under heavy pane output: it jumps around the screen as updates are written | tmux forwards each pane update to the terminal as it happens (`tty.c` `tty_cmd_*`, cursor moved per write) and only brackets them in synchronized output (`?2026`, `tty_sync_start/end`) in some paths (`tty_cmd_syncstart`, `screen-redraw.c:1772`) | The compositor (D14) builds one diffed frame per client tick and writes it in a single burst: cursor hidden at frame start, placed once at the end, the whole frame inside `?2026` when the terminal supports it | none (rendering-only, invisible to scripts) | planned (M1, client compositor) |
| ~~Popup borders flicker when panes under them scroll~~ | Not a defect as stated. tmux 3.8 trims every pane draw to the cells outside the popup (`tty_draw_pane` via `tty_check_overlay_range`, `tty.c:1425-1455`; `tty_cell` skips covered cells, `tty.c:2268-2270`), and its scroll/ICH/DCH paths go through the same trim (`c->overlay_check != NULL` forces `tty_draw_pane`, not a terminal scroll), so pane output never lands in the popup. What tmux does write into the popup rectangle is its own repaint (`popup_draw_cb`, `popup.c:~190-240`) of the same cells on every full client redraw (`CLIENT_REDRAWOVERLAY`: the start timer, a blocked tty draining, a window change): 320 cells in the pinned flood, 72 border writes in a 3000-line `seq` flood. The cells repainted hold what was already there | Popups are composited into the same frame as the panes, so a cell is written only when it changes: during a flood under an open popup vtmux writes 0 cells into the popup rectangle, the reference repaints it. Nothing to fix; pinned by `pane_flood_under_a_popup_writes_nothing_into_it` (`crates/vtmux/tests/attach.rs`, raw byte stream) | none (rendering-only) | not a defect (M1); the byte-count difference stays pinned |
| Large scrollback costs too much RAM, so people keep `history-limit` low | [#3352](https://github.com/tmux/tmux/issues/3352), [#3194](https://github.com/tmux/tmux/issues/3194), [#4859](https://github.com/tmux/tmux/issues/4859), [PR #4013](https://github.com/tmux/tmux/pull/4013); the copy-mode crash in long sessions with big histories ([#4777](https://github.com/tmux/tmux/issues/4777), [#4962](https://github.com/tmux/tmux/issues/4962)) | Keep retained rows close to `history-limit` at any pane width, and compress idle scrollback with libghostty-vt's page compression (restored transparently on read). Spec: `docs/specs/2026-10-31-history-memory.md` | none (performance, invisible to scripts) | done: idle spec scenario 36.6-42.2 MB at 10 s (settled 17.6 MB) against tmux 3.8's 66.0 MB; `copy-mode` entry on compressed history 1.03x uncompressed; steps at most 1.34 ms; busy-pane p95 within 10% on the larger samples ([numbers](test-health/2026-11-03-history-compression-bench.md)); a pane streaming 10-1000 lines/s at the 100k limit holds 18.5-19.8 MB (106.6-109.8 MB before `hist_compress_busy`, tmux 65.7-66.7 MB; [numbers](test-health/2026-11-05-history-compression-busy.md)) |

## vtmux options

All are off until set and invisible to scripts while unset (next section). Guard them in a shared config with `%if "#{vtmux_version}"` so the same `.tmux.conf` loads in real tmux.

| Option | Scope | Values | Default | What it does |
|---|---|---|---|---|
| `vtmux-pane-active-blend` | window | `fg=<colour>[/<pct>],bg=<colour>[/<pct>]` | empty | Blends every cell of the active pane toward the colours (`/pct` 0-100, default 100). `bg`/`fg` as colours mean the outer terminal's default background/foreground |
| `vtmux-pane-inactive-blend` | window | as above | empty | The same, for every other pane of the window. `fg=bg/25,bg=bg/25` dims like Ghostty's `unfocused-split-opacity = 0.75` |
| `vtmux-persist` | server | `off`, `layout`, `full` | `off` | Checkpoints the server to `$XDG_STATE_HOME/vtmux/<socket-name>-<hash>/` (default `~/.local/state`; `<hash>` of the socket's absolute path; directories 0700, files 0600; locked by the writing server) on a clean shutdown (`kill-server`, SIGTERM, the last session gone) and every 60 s while something changed. `layout`: sessions, windows, layout, panes' start command and cwd, options and key bindings, no user content (no screen, title or buffer); `full` adds every pane's screens, history and title (copy mode's for now: pane terminal state is not exported yet) and the paste buffers. Never the message log, environment or prompt history. A server starting on that socket with a checkpoint there restores it before its config runs (`attach` and every command that starts a server; `ls` does not start one): sessions, windows, layout, options and buffers, every pane dead (status unknown) with its dead line, its screen empty for `layout` (screens for `full` once pane terminal state is carried); `respawn-pane` restarts its command in its cwd. A config setting `vtmux-persist off` gets no restore. A checkpoint that can't be read or checked leaves a fresh server, why in `show-messages`, and the files untouched. D27, `docs/specs/2026-11-06-live-upgrade.md` |
| `vtmux-persist-drop` | session | globs (array, as `update-environment`) | empty | User options not restored from a checkpoint, e.g. `set -g vtmux-persist-drop '@murmur_*'` so a tool's state for panes that are now dead does not come back. A session's own value applies to its options, its windows' and panes'; the global one (the config's if it sets it) to the rest. D27 decision 30 |

Example (the owner's two-pane setup):

```tmux
%if "#{vtmux_version}"
set -g vtmux-pane-inactive-blend 'fg=bg/25,bg=bg/25'
%endif
```

## How vtmux options stay invisible

vtmux options live in their own table (`crates/vtmux-core/src/options/vtmux.rs`), not tmux's generated one. They match by exact name only, so tmux's prefix errors (`set -g vt on` → `invalid option: vt`) don't change. A tree holds one only once it is set there: listings (`show -g`, `-gw`, `-A`, …) and `#{name}` formats see it only then, and a named `show` prints the default. `crates/vtmux/tests/cli.rs` `vtmux_options_invisible_while_unset` compares the off state with tmux 3.8.
