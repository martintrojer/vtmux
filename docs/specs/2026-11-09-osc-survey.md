## 0. The policy problem comes first

The owner's goal ("go beyond tmux where Ghostty supports standards tmux lacks") conflicts with the spec as written:
- *Non-goals*: "Native images (passthrough only, see Scope)". *Scope / Out*: "Native image rendering (sixel, Kitty graphics). Images work via `allow-passthrough` only." (docs/specs/2026-10-29-vtmux.md:97, :118-119)
- *Paper-cut fixes*, rule 1: "A new capability is a feature, and features are out." (spec :102)
- *Divergence process*: "There is no `Intentional divergence` category for product reasons: vtmux has no product surface beyond tmux's." (spec :267)
- Everything that answers a pane deliberately answers as tmux. Ghostty's replies are filtered down to tmux's set (`tmux_reply`, V: crates/vtmux-vt/src/term.rs:4501-4526; the dropped list is at term.rs:4480-4500 and pinned by `replies_tmux_does_not_send_are_dropped`, term.rs:4881-4893). `CSI ? u` (kitty keyboard), `?2048`, `?2027`, OSC 21, OSC 5522 and kitty graphics APC are all suppressed on purpose.

So every row below that goes beyond tmux needs a new decision first: a "protocol extensions" track next to paper cuts. That is D28 in section 4. Without it, the only legitimate work in this survey is the parity gap in row 1 (OSC 8 to clients).

## 2. Detail on the items that matter

### 2.1 OSC 8 to clients (parity, no decision needed)
- tmux: `Hls=\E]8;%?%p1%l%tid=%p1%s%;;%p2%s\E\\` (tty-features.c:101); `tty_attributes`/`tty_hyperlink` writes a link whenever the cell's link changes, with ids from `hyperlinks.c` (`tmuxN`).
- vtmux: the grid has full link identity (`LinkState`, capture, `#{copy_cursor_hyperlink}`, `clear-history -H` D-018), but the composed `Cell` keeps only `link: bool` (render/compose.rs:89, 268). D-007 (DIVERGENCES.md:85) records "compositor does not yet write OSC 8".
- Work: carry a link handle (pane id + Ghostty link id, or an interned URI+id) in the composed cell; include it in row equality (share.rs, row cache); have the encoder open and close links around runs, close before every cursor move and at row end (as tmux's `tty_cursor` path does), and send nothing to a client without `Hls`. Oracle: compare frame bytes with tmux for one linked line; also the `id=` param must be tmux's form. Survives upgrade: yes.

### 2.2 Kitty keyboard protocol
- Why it matters: Shift+Enter in Claude Code/Codex, C-i vs Tab, Esc vs Alt in nvim/helix, release events for TUIs. Under tmux users need `extended-keys on` + `extended-keys-format csi-u` + `terminal-features …:extkeys`, and still get no release events or super key.
- Phase 1 (pane side, no outer change):
  - Answer `CSI ? u` from Ghostty's active-screen flags (`Terminal::kitty_keyboard_flags`, libghostty-vt/src/terminal.rs:615).
  - When the flags are non-zero, encode each key that reaches the pane (after key-table lookup, which stays as it is) with `key::Encoder::set_kitty_flags` (key.rs:191), mapping vtmux's `Key` and modifiers to Ghostty's `Key`/`Mods`. Flags 1 (disambiguate), 4 (alternates; needs the shifted key) and 8 (all keys as escapes) can be produced from what vtmux already decodes from the outer modifyOtherKeys 2 input; flag 2 (release) and 16 (text) cannot.
  - `send-keys` goes through the same encoder. **This is the drop-in risk**: mu and murmur `send-keys` into Claude Code. With flag 1, `Enter` stays `\r` and literal text stays text, but `Escape` becomes `CSI 27 u` and `C-c` `CSI 99;5u`, which an app that enabled the protocol handles. Pin with a test driving a stub app that pushes `CSI >1u`.
  - The stack is per screen, so leaving the alternate screen restores the shell's flags (Ghostty semantics, kept in the snapshot, state.rs:98-100).
- Phase 2 (outer): push `CSI >Nu` on the client terminal when it answers `CSI ? u` (Ghostty, kitty, foot, WezTerm), decode kitty input in the client key parser into vtmux keys plus event type, and fall back to tmux's `Eneks` path otherwise. Key-table names (`C-S-x`, `M-Enter`) must come out the same as tmux's for bindings to match. L.
- Option: `vtmux-kitty-keys off|on`. Arguably it could default on (only an app that asks sees a difference: tmux gives it no reply and it falls back), but start with off and flip it after the daily-driver week.

### 2.3 Desktop notifications
- Today's tmux path is `allow-passthrough`, which lets any program write raw bytes to the outer terminal (title spoofing, clipboard writes, OSC 52 reads where allowed). Forwarding natively is the safe subset and needs no app cooperation.
- Parse in vtmux's scanner (the OSC is already seen there: `ProgressBar::osc_9` in vt/progress.rs:66-80): OSC 9 payloads that are not ConEmu subcommands (Ghostty's rule), `777;notify;title;body`, and OSC 99 chunks (`i=`, `d=0/1`, `p=title|body`).
- Deliver to every attached, non-control client whose session holds the window, re-encoded by the client's terminal family (`#{client_termtype}` from XTVERSION, D-007): Ghostty/WezTerm/urxvt get 777, kitty gets 99, iTerm2 gets 9. Title from a `vtmux-notification-title` format, e.g. `#{session_name}:#{window_index} #{pane_title}`. Coalesce floods.
- Optionally also raise the window's bell/activity alert (`monitor-bell` semantics) so the status line shows it. That is close to the agent-integration non-goal, so leave it to the owner.
- Live upgrade: stateless; one in flight during quiesce is lost (acceptable).

### 2.4 In-band resize (2048)
- Ghostty already encodes the report (`size_report.encode(.mode_2048…)`, stream_terminal.zig:533-542). vtmux answers XTWINOPS sizes itself (`PaneTerm::size_report`); give 2048 the same model. Send on `?2048h`, and on every size change after the pty winsize is set. DECRQM: 1/2.
- Risk is completeness: nvim ignores SIGWINCH once 2048 is confirmed, so a missed resize path is a visible bug. Pin it with a test that resizes through every path (split, zoom, `resize-window`, client resize, `swap-pane` between windows, `respawn-pane`, `break-pane`, live-upgrade resume) and checks for the report.

## 3. Ranking (value ÷ effort, with risk)

1. **OSC 8 to clients** (parity, M, no risk): closes a 3.8 gap the owner sees daily (agent file links).
2. **Desktop notifications** (S-M, low risk): background-window agent alerts with passthrough off.
3. **Kitty keyboard, phase 1** (M, medium risk, opt-in): Shift+Enter and friends in Claude Code, nvim and helix with no tmux keyboard config.
4. **In-band resize 2048** (S-M, low risk): nvim resize correctness, races gone.
5. `?2027` reported as set (S code, needs a width audit first).
6. OSC 133 click-to-move (M).
7. OSC 22 pointer shape (M).
8. Kitty keyboard phase 2, outer input (L).
9. Native kitty graphics via unicode placeholders (L-XL; reverses a non-goal; not in the snapshot).
10. OSC 21, OSC 5522, 1337 CurrentDir/Copy (S-M each, low value).
Skip: sixel, OSC 66, DECSCA, OSC 7501/3008, XTWINOPS extensions.

**Recommended first batch (4 items + 1 policy decision):** D28 policy, then OSC 8 emission (no decision needed, closes D-007's hyperlink clause), notifications (D30), kitty keyboard phase 1 (D29), in-band resize (D31). All four are small to medium, reuse state Ghostty already keeps and the snapshot already carries, and change nothing for a program that doesn't ask.

## 4. Spec decisions needed (sketch)

- **D28: Protocol extensions** (amends *Non-goals*, *Paper-cut fixes* rule 1 and the *Divergence process* sentence on product divergences). "vtmux implements a terminal protocol tmux 3.8 ignores when (1) libghostty-vt implements it in the pane terminal and Ghostty implements it as an outer terminal; (2) only a program that uses that protocol (a query, a mode set, or a sequence tmux 3.8 drops) can observe the difference; (3) vtmux's identity stays tmux's: XTVERSION `tmux 3.8`, DA1/DA2, `TERM`, `TERM_PROGRAM=tmux`, `#{version}`; (4) each has a `vtmux-*` option, listed only where set; with it off, vtmux matches tmux byte for byte, pinned by an oracle scenario, and with it on, a test pins vtmux's behaviour; (5) each records in its decision what a live upgrade keeps; (6) each gets a `compat/DIVERGENCES.md` entry, category `Spec decision`." Why: Ghostty in every pane already parses these; tmux drops them, and users route around it with `allow-passthrough`, which is unsafe. Images stay out until a separate decision.
- **D29: Kitty keyboard per pane.** `vtmux-kitty-keys off|on` (server). On: `CSI ? u` answered from the pane's active-screen stack; keys and `send-keys` to a pane with non-zero flags are encoded by libghostty's key encoder from the key vtmux decoded; key tables, `extended-keys` and `#{pane_key_mode}` are unchanged for panes with flags 0. Phase 2 (outer kitty input) is a later decision. Why: tmux#3335 is closed unimplemented, and Shift+Enter is the top agent-TUI complaint under tmux.
- **D30: Desktop notifications.** `vtmux-notifications off|on` + `vtmux-notification-title <format>`. OSC 9 (non-ConEmu), 777;notify and 99 from any pane go to the attached clients of the sessions holding its window, re-encoded per client terminal family, rate-limited; never to control clients; independent of `allow-passthrough`. Why: tmux drops them (input.c:3036), and the only way past is passthrough.
- **D31: In-band resize reports.** Under D28's rules, mode 2048 is supported per pane: DECRQM reports it, `?2048h` and each pane size change write `CSI 48;rows;cols;hpx;wpx t`, with pixels from the window pixel model (D-014). Possibly with no option at all, since only a program that queries and sets 2048 sees it; D28 would need to allow that explicitly.
- Later: **D32** `?2027` reported permanently set (after a width audit against D-031/D-044/D-045); **D33** native kitty graphics via unicode placeholders, reversing the images non-goal, with snapshot blobs or a documented loss on upgrade.

Check against current releases before writing tests.
