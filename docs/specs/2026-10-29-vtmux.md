# vtmux — tmux-compatible multiplexer on Rust + libghostty-vt

Status: approved · Date: 2026-10-29 · Target: tmux 3.8

## Problem

tmux is the right *model* (server, sessions/windows/panes, a command and format language that a whole ecosystem scripts against) on a dated stack: ~111k lines of C, slow release cadence, sharp edges, and an in-house terminal emulator. The alternatives either drop the model (Zellij, WezTerm mux, Rex), drop the multiplexing (shpool, zmx), or are high-velocity rewrites nobody has hardened (rmux: ~680k lines in 5 months; tmux-rs: a stalled, all-`unsafe` transliteration).

The owner's setup depends on tmux's language, not just its features: ~550 lines of config (`.tmux.conf` + mu-crew's `mu-crew.conf`) built on `#{E:}` re-expansion, `@user` options written by external pollers, hooks, popups, control mode; TPM plugins (tmux-yank, tmux-fingers-rs, tmux-fzf, vim-tmux-navigator, tsesh); and tools (murmur, mu) that drive `tmux` as a CLI and via `-C`.

## Pitch

A drop-in replacement for tmux 3.8 on a modern stack: same CLI, config, formats, hooks and control mode; a Rust core with `unsafe` confined to two small modules; terminal emulation by libghostty-vt. First-class Linux. Forkable (ISC).

## Why not Rex

Superlogical's Rex (Mitchell Hashimoto, public beta Oct 2026) shares the libghostty foundation but makes the opposite bet: the client *is* the terminal, no in-window pane tree, Lua config, `.tmux.conf` unsupported. As of 2026-10-29 it is macOS-only for clients, has no stated source license, and the owner has no access. vtmux requires first-class Linux, terminal-agnosticism (works inside any terminal, over plain SSH, on the console) and forkability. **Revisit if** Rex ships a Linux client under an open-source license.

| | Rex | vtmux |
|---|---|---|
| Core idea | Rethink the multiplexer; the client is the terminal | Keep tmux's model, rebuild it on a modern stack |
| libghostty | In every client (server streams raw PTY bytes) | In the server (tmux-style emulator in the middle) |
| Runs inside any terminal, over plain SSH, on the console | Not today; a "legacy mode for dumb terminals" has only been discussed | Yes, by design |
| `.tmux.conf`, TPM plugins, murmur, mu | Need porting to Lua and Rex's API | Work unchanged (the goal) |
| Splits | Native GUI containers, no in-window pane tree | tmux pane tree, plus 3.8 floating panes |
| Config and scripting | Lua `init.lua`, `rex` CLI with `--json`, server API, event stream | tmux config, CLI, formats, hooks, control mode |
| Remote | Built in: real system login over Tailscale identity | SSH in, then attach (as tmux) |
| Linux | Servers in testing; client not public | Primary platform |
| Source and forking | Free, self-hostable, no source license stated | ISC, forkable |
| Maintainer | Funded team led by Ghostty's author | The owner |

Sources: [superlogical.com](https://www.superlogical.com/), [public testing update](https://www.superlogical.com/updates/public-testing-beginning), [Rex Lua docs](https://www.superlogical.com/rex/docs/reference/lua), [bitdoze overview](https://www.bitdoze.com/superlogical-rex/).

## Why not rmux

[rmux](https://github.com/Helvesec/rmux) is the closest existing project: a Rust multiplexer with a tmux-compatible CLI. Facts below come from a shallow clone and the GitHub API on 2026-10-29.

| | rmux | vtmux |
|---|---|---|
| Goal | Programmable multiplexer engine; tmux CLI compatibility is one surface beside typed SDKs (Rust, Python, TypeScript), web sharing and Claude teammate mode | Drop-in tmux 3.8, nothing else |
| Size and pace | ~630k lines of Rust (server crate ~385k, tests ~80k) in ~5 months; ~1,110 commits by one author; 100 commits in 9 days at one point | Small core, small reviewed merges (D16) |
| Terminal emulation | Its own emulator in `rmux-core` (grid, input, screen) | libghostty-vt (D13), so the VT core isn't ours to harden |
| Runtime | tokio, multi-threaded runtime in places | Single-threaded mio loop (D9) |
| `unsafe` | ~500 occurrences across client, ipc, os, pty, server, sdk and core | Confined to `vtmux-vt` and the server's `sys` module (D10) |
| Config | Own config first; `tmux.conf` parsed on a "best-effort" fallback, and unsupported plugin lines get skipped | `tmux.conf` and TPM plugins are the primary config (D6) |
| Compliance evidence | Head-to-head probes against tmux 3.7b, a divergence ledger, conformance key lists, its own Rust tests. It does **not** run tmux's `regress/` suite | tmux 3.8 `regress/` verbatim + recorded oracle traces + esctest (triangulation) |
| Platforms | Linux, macOS, Windows (ConPTY) | Linux first, macOS second, no Windows |
| License | MIT OR Apache-2.0 | ISC |

What we take from it:
- Its divergence categories (`ISO required` / `Intentional divergence` / `Do not copy tmux bug` / `Deferred`) are a good taxonomy. Adopt them in `DIVERGENCES.md`, with a mandatory evidence field.
- Its conformance lists (format tokens, `list-*` keys, control notifications) make useful seed input for oracle scenarios. They're under MIT/Apache, so we can use them with attribution.
- Its `argv[0] == "tmux"` handling (tmux-style `-V`, honouring `$TMUX`) confirms D1 and D5.

Why not contribute to or fork it instead: its scope (SDKs, web sharing, Windows) and size make it the opposite of a small, hardened core. It has its own emulator where we want libghostty. And its compatibility claim rests on its own tests, not on tmux's. Forking it would mean inheriting ~630k lines to review.

The pitch against rmux in one line: **less code, tmux's own test suite, Ghostty's emulator.**

## Scope

In (eventually, M2): everything tmux 3.8 does that is observable through the CLI, config, control mode or the attached screen — including floating panes.

Out:
- Native image rendering (sixel, Kitty graphics). Images work via `allow-passthrough` only.
- Windows. Linux is primary; macOS supported and CI-gated, second.
- tmux's imsg wire protocol. A real `tmux` client cannot attach to a vtmux server.
- iTerm2 `-CC` integration polish (plain `-C` is in).
- Anything only on tmux master after 3.8, until a deliberate target bump.

## Key decisions

| # | Decision | Why |
|---|---|---|
| D1 | Name `vtmux` (VT = video terminal, as in VT100 / libghostty-vt). Own binary, own socket dir `$TMUX_TMPDIR/vtmux-UID`, optional `tmux → vtmux` symlink | Runs side by side with real tmux (needed for the oracle); `gmux` was taken twice in this space |
| D2 | Compatibility surface = CLI, config syntax, formats, options, hooks, key tables, control mode, `$TMUX`, env. Internal client/server protocol is our own | Nothing in the ecosystem speaks imsg; matching it would freeze tmux internals |
| D3 | Pinned target: tmux **3.8** regress suite and behaviour. Bumps are deliberate | A moving target makes the scoreboard meaningless |
| D4 | **Grid follows Ghostty; everything else follows tmux exactly.** Serialization (`capture-pane`, `pane_*` formats, cursor reporting) is shaped like tmux even when the cells came from Ghostty. Arbiter for grid disputes: esctest/vttest vs xterm → ECMA-48/xterm ctlseqs → consensus of Ghostty/xterm/kitty. No arbiter verdict → match tmux | Scripts parse serialized output; screen correctness has an external authority; compatibility is the pitch, so ties go to tmux |
| D5 | Inside panes, a shim dir with `tmux → vtmux` is prepended to `PATH`; `$TMUX` uses tmux's `socket,pid,session` shape | Plugins call `tmux` and read `$TMUX`; drop-in must not depend on the user's PATH |
| D6 | Config search order identical to tmux (`~/.tmux.conf`, `$XDG_CONFIG_HOME/tmux/tmux.conf`, …; `-f` overrides) | Existing config loads unmodified |
| D7 | `default-terminal` honoured exactly, default `tmux-256color` | Universal terminfo; libghostty supports everything it advertises |
| D8 | Outer-terminal output driven by `terminal-features`/`terminal-overrides`/terminfo, not by assuming Ghostty | Part of compliance; required for SSH, nested, console |
| D9 | Single-threaded event loop (`mio`); blocking work (`run-shell`, `if-shell`, `#()`) in child processes | tmux semantics assume strict command ordering; deterministic tests; small core |
| D10 | `unsafe` only in `vtmux-vt` and the server's `sys` module (PTY, fork/exec, signals). All other crates `#![forbid(unsafe_code)]` | The memory-safety argument, enforced from day one |
| D11 | Behaviour-faithful, not code-faithful: tmux C is read as the spec; Rust internals are free (ID arenas, not pointer graphs) | Line-by-line porting is how tmux-rs ended up all-`unsafe` and stalled |
| D12 | Hand-written recursive-descent command parser, verified by `cmd-parse-*` regress + oracle + fuzzing | Better errors, no generator; the grammar (`cmd-parse.y`, ~1.9k lines) is small |
| D13 | `libghostty-vt` crate, exact version pin. Vendor + patch (herdr-style per-patch log, upstream PRs) only when a bug can't wait | Least maintenance until there's a reason; herdr shows the C API still moves |
| D14 | Server composites and encodes frames per client capability and sends bytes over the socket; client is a dumb pipe (no tty fd passing) | Same semantics as tmux, controllable per-client backpressure, remote clients possible later |
| D15 | Window layout model = tiled tree **plus a z-ordered floating layer from day one**; layout strings parse/emit 3.8's JSON-subset format | Floating panes shipped in 3.8 and appear in ~19 regress tests, many of them core ones; retrofitting a layer into a tiling-only model is a rewrite |
| D16 | Process: agents may write code; every merge is human-reviewed, small, and gated green on regress + oracle | "Not vibe-coded" is part of the pitch; the oracle is an independent check agents can't grade themselves against |
| D17 | ISC license | Matches tmux; vendoring its regress suite and reading its source are friction-free |
| D18 | Rust edition 2024, stable pinned in `rust-toolchain.toml`, clippy pedantic in CI, Zig pinned via mise | Reproducible builds; libghostty-vt needs Zig |
| D20 | Socket directory depends on the invoked name: run as `tmux` (symlink) → tmux's `$TMUX_TMPDIR/tmux-UID`; run as `vtmux` → `vtmux-UID`. Error messages match tmux byte for byte under either name | murmur and mu build `tmux-UID` themselves and match `no server running on …` / `error connecting to …`; calls from outside a vtmux pane never see the D5 shim. Refines D1 |
| D21 | Version: as `tmux`, `-V` prints `tmux 3.8`; as `vtmux`, `vtmux X.Y.Z (tmux 3.8)`. `#{version}` is always `3.8`. Own identity via `VTMUX_VERSION` env and `#{vtmux_version}` | Plugins (tmux-yank etc.) gate features on `tmux -V`; anything else silently degrades them |
| D22 | Grid divergences do not block M1. M1 screen scenarios cover what the multiplexer draws (status, borders, popups, copy-mode highlight) over pane content both emulators agree on; grid mismatches found in M1 get a `Deferred` D-NNN. Arbiter tooling (esctest/vttest) lands in M2 | Keeps M1 a daily-driver milestone, not an emulator-conformance project |
| D19 | Repo `~/hacking/vtmux`, jj colocated with git, personal GitHub (`martintrojer/vtmux`) once the walking skeleton works; mu-crew later if warranted | Don't announce a drop-in before it is one |

## Architecture

```
vtmux (bin)      CLI parse → run a command against the server, or attach
├─ vtmux-core    pure, no I/O, no unsafe: command parser, command table, targets,
│                options (scopes, arrays, user options), formats, styles, key tables,
│                layout strings. Most of tmux's semantics live here.
├─ vtmux-vt      the only FFI crate: safe wrapper over libghostty-vt, plus tmux-shaped
│                serialization (capture-pane -p/-e/-J, pane_* values, cursor).
├─ vtmux-server  mio event loop; sessions/windows/panes in ID arenas ($N @N %N);
│                PTYs; job runner; hooks; control-mode clients; compositor
│                (panes + borders + status + popups + floating layer → frame);
│                per-client encoder driven by terminal-features.
└─ vtmux-client  attach: raw tty, forward input bytes, write frames, resize/signals.
```

Runtime: the first command starts a background server at `$TMUX_TMPDIR/vtmux-UID/<label>` (`-L`/`-S` as tmux). Each invocation connects, sends argv/cwd/env/tty info, gets output and an exit code; `attach` keeps the connection open. libghostty's `on_pty_write` callback routes terminal query replies (DA, DSR, …) back into the pane's PTY.

## Compliance: triangulation

Three independent sources of truth:

| Source | Tells us | Authoritative for |
|---|---|---|
| tmux 3.8 `regress/` | what tmux is meant to do | intent and chosen edge cases |
| Behaviour oracle | what tmux 3.8 actually does | everything observable via CLI, control mode, attached screen |
| esctest / specs | what a correct terminal does | the pane grid (D4) |

### Regress harness

```
compat/
  tmux-3.8/regress/   vendored verbatim from tag 3.8, never edited
  patches/            one minimal patch per divergent assertion
  expected.toml       per test: pass | xfail(reason, link) | skip(out-of-scope)
  DIVERGENCES.md      D-NNN: test/assertion, tmux behaviour, vtmux behaviour, evidence
```

`cargo xtask regress`: copy suite to a temp dir, apply patches, run each test with `TEST_TMUX=target/debug/vtmux` under `env -i` (as tmux's Makefile does), in parallel. Fails on unexpected failures **and** unexpected passes. Prints a scoreboard and writes JSON for trend tracking. `--update` only records fail→pass flips; adding an xfail is a manual, reviewed edit.

At tag 3.8 the suite has 174 tests; 84 need an attached client or control mode. Tests from tmux master may run on a separate, non-gating "preview" scoreboard.

### Behaviour oracle

```
oracle/
  scenarios/   declarative: setup, steps (CLI commands, keys via attached client,
               bytes into a pane, resizes, sync points), observations
  traces/      golden traces recorded from real tmux 3.8, committed, tagged with tmux version
  harvest/     gitignored raw logs from the harvest shim
```

`cargo xtask oracle` modes:
- `record` — run scenarios against pinned tmux 3.8, write normalized traces.
- `replay` — run the same inputs against vtmux and diff against traces. No tmux needed; this is what CI runs.
- `live` — record and replay side by side, nothing saved; for exploration and bisecting.
- `harvest` — turn logs from an opt-in logging `tmux` shim (real invocations from plugins, murmur, mu) into candidate scenarios.

Observations: CLI stdout/stderr/exit code; ordered control-mode notification stream; format/option queries; **the attached client's screen**, obtained by running the multiplexer attached in a PTY and feeding its output into a libghostty-vt observer terminal, then comparing the resulting grid — not the raw escape bytes, which legitimately differ.

Sync: wait for quiescence (no PTY output and no pending jobs for N ms) plus `wait-for` channels where possible. No fixed sleeps.

Normalization: pids, socket paths, timestamps, tty names and similar volatile values are rewritten to placeholders before diffing.

A trace step may carry `divergence = "D-NNN"`; replay then expects vtmux's behaviour for that step.

Corpus growth: a scenario with every feature and every bug fix; harvested real-world patterns; generated cases from tmux's `fuzz/*.dict` and from the owner's config formats. Bumping past 3.8 = re-record all traces; the trace diff is a precise changelog of tmux behaviour changes.

Privacy: harvested logs stay local; a scenario is committed only after manual review with paths and contents replaced by synthetic ones.

### Fuzzing

`cargo-fuzz` targets per core parser (commands, formats, styles, layouts), seeded from tmux's dictionaries. Nightly, not per PR.

### CI (GitHub Actions)

Per PR, Linux: fmt, clippy pedantic, unit tests, `xtask regress`, `xtask oracle replay`. macOS: same minus fuzzing, required. Scoreboard posted on the PR. Real tmux 3.8 is built from the tag and cached (used by `record`/`live`; locally via `$VTMUX_REFERENCE_TMUX`, else built).

### Divergence process

1. Regress or oracle mismatch.
2. Classify: (a) vtmux bug → fix; (b) grid-level difference → run the D4 arbiter; (c) libghostty bug → patch, log, upstream.
3. If (b) and Ghostty wins → `D-NNN` in `DIVERGENCES.md` with evidence, plus a regress patch or trace annotation. No verdict → match tmux.

Each `D-NNN` carries a category, borrowed from rmux: `Ghostty grid` (D4 arbiter ruled), `Do not copy tmux bug` (tmux loses data, hangs or is unsafe; needs evidence and a regression test), or `Deferred` (not done yet; must not be claimed as compatible). There is no `Intentional divergence` category for product reasons: vtmux has no product surface beyond tmux's.

## Milestones

**M0 — walking skeleton.** Server, one session, one pane on libghostty-vt, `attach`/detach, `-C` control mode, `display-message -p`, `capture-pane -p`, end to end and thin. Harness and oracle `record`/`replay` running against it. (Half the 3.8 suite needs attach or control mode, so these come first.)

**M1 — daily driver.** During the daily-driver week real tmux stays installed but does not own the default `tmux-UID` server (D20); the oracle runs real tmux under its own `TMUX_TMPDIR`. The owner's unmodified `.tmux.conf`, `mu-crew.conf`, TPM plugins, murmur and mu work, with `tmux` symlinked to vtmux. Surface, derived from what these actually call:

| Area | Scope |
|---|---|
| Commands (~40) | murmur: `set-option`, `display-message`, `list-panes/-sessions/-windows`, `switch-client`, `new-session`, `show-options`, `send-keys`, `refresh-client`, `capture-pane`, `load-buffer`, `paste-buffer`, `kill-pane`, `kill-session`, `split-window`, `select-pane`, `resize-pane`, `new-window`. mu: `send-keys`, `-C`, `new-session`, `kill-pane`, `respawn-pane`, `has-session`, `display-message`, `new-window`, `list-*`, `capture-pane`, `switch-client`, `split-window`, `set-option`, `kill-session`. Config/plugins: `select-pane`, `copy-mode`, `send-keys`, `run-shell`, `split-window`, `swap-pane`, `resize-pane`, `display-popup`, `choose-tree`, `break-pane`, `move-pane`, `command-prompt`, `select-layout`, `if-shell`, `source-file`, `set-hook`, `set-environment`, `bind`/`unbind`. Plus basics: `kill-server`, `list-keys`, `list-commands`, `start-server`, `attach`, `detach` |
| Formats | variables, `@user` options, `E:`, `==`, `!=`, `e\|op\|`, `m:`, `\|\|`, `&&`, `b:`, `d:`, `T:`, `#{?}`, `#[style]`, `#()` jobs |
| Options | all scopes; `-g -u -F -a -o -q`; arrays (`terminal-features[N]`); user options |
| Hooks | `after-select-pane`, `after-select-window`, `client-session-changed`, generic `after-*` |
| Keys | prefix/root/custom tables (`-T`), `-n`, `-r`, `-N`, `extended-keys csi-u`, mouse |
| Client/UI | status (left/centre/right, `status-interval`), pane borders + `pane-border-format`, `display-popup -E`, `display-message`, `choose-tree`, `command-prompt`, vi copy mode + `copy-pipe`, `allow-passthrough`, OSC 52, `set-titles` |
| Control mode | `-C` with `%begin/%end/%error`, `%output`, `%window-*`, `%session-*` as mu uses them |

Done when: (1) a week of the owner's daily work on vtmux without blocking bugs; (2) every M1 area has green oracle scenarios; (3) regress scoreboard tracked and non-regressing (no number required).

Not in M1: floating panes, `choose-buffer`/`choose-client`, `customize-mode`, `clock-mode`, session groups, `pipe-pane`, `display-menu`, emacs copy mode, `lock-*`, emacs status-keys.

**M2 — 3.8 compliance.** Every in-scope 3.8 regress test passes or is a documented divergence. Includes floating panes (D15).

**M3 — public.** Announcement and packaging (crates.io, Fedora COPR, Homebrew). Not before M2.

## Open questions

- Exact layout of the client/server protocol (framing, versioning). Builder's call within D14.
- libghostty-vt gaps for tmux serialization (e.g. tmux-style `capture-pane -J` joined lines, `-e` SGR shape) — discovered during M0; may force the first vendored patch.
- How faithfully to mirror tmux's terminfo-driven encoder vs a capability table built once per client. Builder's call within D8.
