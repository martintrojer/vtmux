# vtmux — tmux-compatible multiplexer on Rust + libghostty-vt

> **tmux on a modern stack: all the baggage, fast and lean, fewer paper cuts, better rendering.**

Status: approved · Date: 2026-10-29 · Target: tmux 3.8

## Problem

tmux is the right *model* (server, sessions/windows/panes, a command and format language that a whole ecosystem scripts against) on a dated stack: ~111k lines of C, slow release cadence, sharp edges, and an in-house terminal emulator. The alternatives either drop the model (Zellij, WezTerm mux, Rex), drop the multiplexing (shpool, zmx), or are high-velocity rewrites nobody has hardened (rmux: ~680k lines in 5 months; tmux-rs: a stalled, all-`unsafe` transliteration).

The owner's setup depends on tmux's language, not just its features: ~550 lines of config (`.tmux.conf` + mu-crew's `mu-crew.conf`) built on `#{E:}` re-expansion, `@user` options written by external pollers, hooks, popups, control mode; TPM plugins (tmux-yank, tmux-fingers-rs, tmux-fzf, vim-tmux-navigator, tsesh); and tools (murmur, mu) that drive `tmux` as a CLI and via `-C`.

## Pitch

A drop-in replacement for tmux 3.8 on a modern stack: same CLI, config, formats, hooks and control mode; a Rust core with `unsafe` confined to two small modules; terminal emulation by libghostty-vt. First-class Linux. Forkable (ISC).

**Why it exists: the paper cuts.** tmux has usability defects that have sat in its backlog for years, often because fixing them in tmux's C would break someone. vtmux fixes them without breaking compliance: every fix is opt-in or invisible to scripts, so a tmux config, plugin or script sees exactly tmux 3.8. The focus ring (D23, since removed, superseded by pane blend, D26) was the first and the model for the rest.

Just the core. Zellij, herdr, TUIOS and most of the field grow by stacking features. vtmux goes the other way: tmux's behaviour, done solidly, plus fixes for tmux's own rough edges, plus (opt-in) the terminal protocols Ghostty implements and tmux drops (D28), and nothing else. Images pass through to your terminal, or (opt-in, D33) vtmux draws kitty graphics itself.

## Why not Rex

Superlogical's Rex (Mitchell Hashimoto, public beta Oct 2026) shares the libghostty foundation but makes the opposite bet: the client *is* the terminal, no in-window pane tree, Lua config, `.tmux.conf` unsupported. As of 2026-10-29 it is macOS-only for clients, has no stated source license, and the owner has no access. vtmux requires first-class Linux, terminal-agnosticism (works inside any terminal, over plain SSH, on the console) and forkability. **Revisit if** Rex ships a Linux client under an open-source license.

| | Rex | vtmux |
|---|---|---|
| Core idea | Rethink the multiplexer; the client is the terminal | Keep tmux's model, rebuild it on a modern stack |
| libghostty | In every client (server streams raw PTY bytes) | In the server (tmux-style emulator in the middle) |
| Runs inside any terminal, over plain SSH, on the console | Not today; a "legacy mode for dumb terminals" has only been discussed | Yes, by design |
| `.tmux.conf`, TPM plugins, murmur, mu | Need porting to Lua and Rex's API | Work unchanged (the goal) |
| Splits | Native GUI containers, no in-window pane tree | tmux pane tree, plus 3.8 floating panes |
| Config and scripting | Lua `init.lua`, `rex` CLI with `--json`, server API, event stream | tmux config, CLI, formats, hooks, control mode |
| Remote | Built in: real system login over Tailscale identity | SSH in, then attach (as tmux) |
| Linux | Servers in testing; client not public | Primary platform |
| Source and forking | Free, self-hostable, no source license stated | ISC, forkable |
| Maintainer | Funded team led by Ghostty's author | The owner |

Sources: [superlogical.com](https://www.superlogical.com/), [public testing update](https://www.superlogical.com/updates/public-testing-beginning), [Rex Lua docs](https://www.superlogical.com/rex/docs/reference/lua), [bitdoze overview](https://www.bitdoze.com/superlogical-rex/).

## Why not rmux

[rmux](https://github.com/Helvesec/rmux) is the closest existing project: a Rust multiplexer with a tmux-compatible CLI. Facts below come from a shallow clone and the GitHub API on 2026-10-29.

| | rmux | vtmux |
|---|---|---|
| Goal | Programmable multiplexer engine; tmux CLI compatibility is one surface beside typed SDKs (Rust, Python, TypeScript), web sharing and Claude teammate mode | Drop-in tmux 3.8, nothing else |
| Size and pace | ~630k lines of Rust (server crate ~385k, tests ~80k) in ~5 months; ~1,110 commits by one author; 100 commits in 9 days at one point | Small core, small reviewed merges (D16) |
| Terminal emulation | Its own emulator in `rmux-core` (grid, input, screen) | libghostty-vt (D13), so the VT core isn't ours to harden |
| Runtime | tokio, multi-threaded runtime in places | Single-threaded mio loop (D9) |
| `unsafe` | ~500 occurrences across client, ipc, os, pty, server, sdk and core | Confined to `vtmux-vt` and the server's `sys` module (D10) |
| Config | Own config first; `tmux.conf` parsed on a "best-effort" fallback, and unsupported plugin lines get skipped | `tmux.conf` and TPM plugins are the primary config (D6) |
| Compliance evidence | Head-to-head probes against tmux 3.7b, a divergence ledger, conformance key lists, its own Rust tests. It does **not** run tmux's `regress/` suite | tmux 3.8 `regress/` verbatim + recorded oracle traces + esctest (triangulation) |
| Platforms | Linux, macOS, Windows (ConPTY) | Linux first, macOS second, no Windows |
| License | MIT OR Apache-2.0 | ISC |

What we take from it:
- Its divergence categories (`ISO required` / `Intentional divergence` / `Do not copy tmux bug` / `Deferred`) are a good taxonomy. Adopt them in `DIVERGENCES.md`, with a mandatory evidence field.
- Its conformance lists (format tokens, `list-*` keys, control notifications) make useful seed input for oracle scenarios. They're under MIT/Apache, so we can use them with attribution.
- Its `argv[0] == "tmux"` handling (tmux-style `-V`, honouring `$TMUX`) confirms D1 and D5.

Why not contribute to or fork it instead: its scope (SDKs, web sharing, Windows) and size make it the opposite of a small, hardened core. It has its own emulator where we want libghostty. And its compatibility claim rests on its own tests, not on tmux's. Forking it would mean inheriting ~630k lines to review.

The pitch against rmux in one line: **less code, tmux's own test suite, Ghostty's emulator.**

## Why not tmux-rs

[tmux-rs](https://github.com/richardscollin/tmux-rs) is the other "tmux, but Rust" project. Facts from a full clone and the GitHub API on 2026-10-29.

What it is: a transliteration of tmux's C into Rust, started from tmux's own git history (forked around Sept–Oct 2024; tmux's ~10k commits are its history, Collin Richards' ~545 are the port). One author, a hobby ("my gardening for the past year"). Its README warns it is alpha, "almost entirely unsafe Rust" with "frequent crashes".

| | tmux-rs | vtmux |
|---|---|---|
| Approach | Line-by-line port of tmux's C, same structures and pointer graph, then incremental refactoring toward idiomatic Rust | Behaviour-faithful rewrite; tmux C read as the spec (D11) |
| Base version | tmux master as of ~Oct 2024 (pre-3.6), not re-synced since | tmux 3.8, pinned (D3) |
| Size | ~79k lines of Rust | Target: well under that; most semantics in a pure `vtmux-core` |
| `unsafe` | ~4,700 occurrences, across the codebase | Confined to two modules (D10) |
| Terminal emulation | tmux's own grid and input parser, ported | libghostty-vt (D13) |
| Runtime deps | libevent and terminfo, as tmux (via libc FFI) | Pure Rust plus libghostty-vt; no libevent |
| Compliance evidence | tmux's regress suite re-added Dec 2025, committed as "failing"; no scoreboard | 3.8 regress + oracle + esctest, gated in CI |
| Activity | Last commit Feb 2026; 51 commits in 2026; 23 open issues | New |
| License | tmux's ISC (repo shows NOASSERTION) | ISC |

What it proves, and what we take from it:
- **The transliterate-then-refactor path stalls.** After ~14 months the code is still ~4,700 `unsafe` sites and alpha. Each refactor has to preserve tmux's pointer-shaped design, so the safety win arrives last, if at all. This is the evidence behind D11.
- **Its CHANGELOG is a bug list for porting C**: wrong bitwise negation, a shadowing memory leak, a mistranslated `strrchr`, subtraction overflow in grid code. Those are the bug classes D10 and D11 are designed to make impossible rather than fixable.
- **Same socket instinct.** It moved to `/tmp/tmux-rs-UID`, like D1's `vtmux-UID`. We add D20 (`tmux-UID` when invoked as `tmux`), which tmux-rs lacks, so it is not drop-in for tools like murmur and mu.
- **Not a base to build on.** Forking it means owning ~79k lines of mostly-`unsafe` C-shaped Rust pinned to a pre-3.6 tmux, then re-porting two years of upstream (floating panes, JSON layouts, everything since). Reading tmux 3.8's C directly is cheaper and starts from the right version.
- **Still useful as a reference.** Where tmux's C is hard to read (macro-heavy, `RB_*`/`TAILQ_*` traversal), tmux-rs's translation of the same function can be a second reading. It's never the spec: tmux 3.8 is.

## Non-goals and feature policy

Not now, not later:
- Agent integration (status detection, agent APIs, sidebars). murmur and mu already do this on top of tmux's language.
- TUI chrome beyond what tmux draws: no dashboards, launchers, welcome screens or session managers.
- Relaunching commands to recreate lost state (resurrect-style command guessing). Restoring state vtmux itself holds (D27: sessions, layout, screens and history, opt-in) is allowed; processes are never recreated, except that an opt-in (`vtmux-persist-respawn auto`) starts a restored pane's default shell again in its directory (live-upgrade spec, decision 32).
- Animations.
- A plugin system of our own. TPM plugins work because tmux's command language works.
- Native images other than kitty graphics (D33). Sixel fails D28's rule 1; other images go by passthrough (see Scope). Images are never in the snapshot (D33).

### Paper-cut fixes

Fixing tmux's long-standing paper cuts is the point of the project. A fix qualifies when it passes all of:
1. **It fixes a defect in something tmux already does.** Confusing, broken or hostile behaviour (the half-coloured active-pane border is the canonical example). A new capability is a feature, and features are out. The one exception is a terminal protocol tmux drops, under D28's rules (*Protocol extensions*), not these.
2. **Compliance holds.** Either it is opt-in (a `vtmux-*` option, off by default) and with it off nothing a tmux script, plugin, oracle trace or regress test observes changes; or it is invisible to scripts by nature (rendering-only, performance, crash or hang fixes).
3. **It has a source.** Each fix names the tmux issue, mailing-list thread or recurring complaint it addresses, so the backlog stays a backlog and not a wish list.
4. **It is recorded.** An entry in `docs/PAPERCUTS.md` (what, why, the tmux reference, the option name or why none is needed) and a test that pins both the fixed behaviour and the unchanged default.

Done: pane blend (D26); the focus ring (D23) was done and then removed 2026-11-06. Candidates are collected in `docs/PAPERCUTS.md` and taken one at a time, after M1, each as its own small spec.

### Bugs fixed

Separate from paper cuts: where tmux itself is wrong (loses data, hangs, is unsafe), vtmux fixes it by default under the `Do not copy tmux bug` divergence category, with evidence, a regression test and a `compat/DIVERGENCES.md` entry. Everything else matches tmux, quirks included.

### Protocol extensions (D28)

Owner, 2026-11-09. Source: `docs/specs/2026-11-09-osc-survey.md`. Every pane runs libghostty-vt, which already implements terminal protocols that tmux 3.8 drops. Users get around tmux with `allow-passthrough`, which lets any program write anything to the outer terminal. vtmux may implement such a protocol when all of these hold:

1. **Ghostty implements it on both sides.** The pinned libghostty-vt (`third_party/libghostty-rs/VENDOR.md`) implements it in the pane terminal, and Ghostty implements it as the outer terminal. Being parsed is not enough: a sequence that reaches libghostty's `unimplemented OSC callback` (stream.zig:3016-3017: OSC 66, OSC 99) does not qualify. Each decision cites the libghostty source that implements it.
2. **Only a program that asks sees a difference.** Asking means sending the sequence, setting the mode or querying it. Scripts, plugins, config, formats, `show-*`/`list-*` output, regress tests and oracle traces still see tmux 3.8.
3. **vtmux keeps tmux's identity.** XTVERSION stays `tmux 3.8`, DA1/DA2 and `TERM` (`default-terminal`) stay tmux's, and so do `TERM_PROGRAM=tmux` and `#{version}` (D21, D25). A program finds an extension only through that protocol's own query or reply.
4. **Each extension has a `vtmux-*` option**, with D23's rules (own table, exact names only, listed only where set). The first batch (D29-D31) defaults off, and each default flips to on after daily use, by an owner decision recorded here. With the option off vtmux matches tmux byte for byte, pinned by an oracle scenario recorded from tmux 3.8. With it on, a test pins vtmux's behaviour. Every extension gets an option, even one only querying programs can see: a default-off stage is how a missed path shows up before it matters.
5. **A grant outlives the option.** The option decides what vtmux answers when a program asks. Once a program is granted an extension, it keeps it until the program turns it off or exits. Turning the option off or on, by `set` or by a live upgrade into a build with another default, changes nothing for a program already running. So no program loses an extension it relies on, or gets one it never confirmed. Each decision says what its grant is.
6. **Each states what a live upgrade keeps** (D27). A new snapshot field is ignorable unless an ordinary session can never produce it (live-upgrade spec, *Required and ignorable fields*). An ignorable field's case goes into `an_ordinary_attached_client_requires_no_feature`.
7. **Each gets a `compat/DIVERGENCES.md` entry**, category `Extension (D28)`, naming the option and the scenario that pins it off.

Not covered yet: OSC 99 and OSC 66, because libghostty doesn't implement them (rule 1); OSC 7501 agent status, an agent-integration non-goal. Kitty keyboard input from the outer terminal (release events, associated text) is a later decision.

#### D29: kitty keyboard protocol, pane side

- **Option:** `vtmux-kitty-keys off|on`, server, default off.
- **Behaviour (on):** `CSI ? u` is answered with the flags of the pane's active screen, of those vtmux applies (1, 4 and 8, see below). A screen is granted once its program pushes or sets non-zero flags (`CSI > f u`, `CSI = f;m u`) while the option is on. While a screen is granted, every key that reaches the pane is encoded by libghostty's key encoder with that screen's flags. That covers keys from an attached client (after the key-table lookup, which doesn't change) and `send-keys` key names. vtmux builds each key from the key it decoded from the client. `send-keys -l`/`-H`, pastes and `#{pane_key_mode}` stay as tmux has them. The grant follows the program's own push, pop and set, whatever the option says. It ends when the stack is back to 0, when the process group that pushed it has no process left (a program killed without popping, 2026-11-10: the pane remembers the PTY's foreground group when a screen's flags first went non-zero, and empties that screen's stack once the group is gone, before the next key is encoded or output parsed; a running program, stopped or in the background too, keeps its grant, rule 5; a program in the pane's own process group, which is the pane's process exec'd or a program of a shell without job control, is tracked like any other and keeps its grant while that group has a process, that is until the pane ends: a shell that outlives a program killed in that group (`bash -c 'prog; prog2'`, `prog; exec bash`) keeps the grant until a `reset`, as the pane cannot tell which process of a shared group pushed), at the program's RIS (which empties both screens' stacks, as Ghostty's full reset does, so `reset` gives a shell tmux's keys back) or when the pane is respawned. Each screen has its own stack (Ghostty), so leaving the alternate screen gives the shell its own flags back. Flags 2 (release events) and 16 (associated text) need kitty input from the outer terminal, so they wait for that later decision; flags 1, 4 and 8 come from what vtmux already decodes.
- **Off:** pushes, pops, sets and queries get nothing back and change nothing vtmux encodes, as in tmux.
- **tmux 3.8:** the CSI table's only `u` entry has no prefix (`INPUT_CSI_RCP`, input.c:347). So `CSI > f u`, `CSI < u`, `CSI = f;m u` and `CSI ? u` are ignored and get no reply. Keys go through `input_key` (input-keys.c:574) with `extended-keys` (modifyOtherKeys, `CSI > 4;N m`) and `extended-keys-format`. tmux#3335 was closed unimplemented. With the option off vtmux drops the sequences before Ghostty sees them (vtmux-vt term.rs `ScanEvent::Kitty`; `replies_tmux_does_not_send_are_dropped`).
- **Ghostty evidence:** inside, the stack is kept per screen (stream_terminal.zig:719-723), the query is answered (`queryKittyKeyboard`, stream_terminal.zig:784, 1963-1970), and the encoder applies the flags (`encode`/`kitty`, input/key_encode.zig:82-100; Rust `key::Encoder::set_kitty_flags`, libghostty-vt key.rs:191; `Terminal::kitty_keyboard_flags`, terminal.rs:615). As the outer terminal: termio/stream_handler.zig:322 and the push/pop/set arms after it.
- **Live upgrade:** Ghostty's stack is already in the snapshot (vtmux-vt term/state.rs `kitty_flags`, `kitty_index`), and it is the grant: a push or set reaches a screen's stack only while the option is on or the screen is granted, so a screen is granted exactly while its flags are non-zero. No new snapshot field (amended 2026-11-09 at implementation: a separate grant field could disagree with the stack it describes). A downgrade to a build without D29 keeps the stack but encodes as tmux and drops the protocol's sequences; an upgrade back grants the screen again. The pushing group is kept per screen in the pane record (`kitty_owner_primary`, `kitty_owner_alternate`; ignorable, so `an_ordinary_attached_client_requires_no_feature` covers it): a grant whose group is gone is dropped on import, and a stack with no recorded group (a build before, or a downgrade and back, in which the program may have ended unseen) is settled on import: the foreground group becomes the pusher, the pane's own process group included (a program exec'd as the pane, as mu launches agents, is that group for its whole life, and rule 5 forbids dropping a running program's grant; amended 2026-11-10); the primary screen not in use is the shell's and kept as it is, the alternate one's is dropped.
- **Tests:** an oracle scenario, off: a stub program pushes `CSI >1u`, queries `CSI ? u`, then gets Escape, C-c and Enter from `send-keys` and an attached client, and its bytes match tmux's. With it on: the reply; Escape is `CSI 27u`, C-c `CSI 99;5u`, Enter `\r`, text stays text; key tables and the prefix still match; a pop to 0 and an alternate-screen exit give tmux's encoding back; a push while off stays legacy after `set vtmux-kitty-keys on`; turning the option off keeps a granted program's encoding; a granted pane keeps it across `vtmux-upgrade`.

#### D30: desktop notifications (OSC 9, OSC 777)

- **Option:** `vtmux-notifications off|on`, server, default off.
- **Behaviour (on):** libghostty decides what counts as a notification from a pane: OSC 9 that is not a ConEmu subcommand (so `9;4` stays progress) and `OSC 777;notify;title;body`. vtmux sends each one, in the form the pane used (libghostty reports only a title and a body: a title means 777, and an empty-title 777, the same notification to Ghostty, goes as OSC 9 unless Ghostty would read that as a ConEmu command), to every attached client of every session that holds the pane's window, whether that window is current or not. A `display-popup -E` program's go the same way to the one client its popup is drawn on (a popup has no window). It goes only to clients whose terminal identifies as Ghostty (its XTVERSION reply, `#{client_termtype}`). Never to a control client. Another terminal is added only with evidence that it shows that form. Each client is rate-limited as Ghostty limits itself: one a second, and an identical one at most once in 5 s (`showDesktopNotification`, Surface.zig:6612-6647). Only a notification that is written counts: one dropped for a client whose terminal is blocked, as passthrough is (`tty_add`), uses none of its limit. This doesn't depend on `allow-passthrough`, which works as before, and a notification that arrived by passthrough is not sent a second time. Grant: none. The option is read at each notification.
- **Off:** dropped, as in tmux.
- **tmux 3.8:** `input_osc_9` (input.c:3030-3037) handles only `9;4`. `input_exit_osc` (input.c:2699-2789) has no 777 or 99 and logs them as unknown. They get out only by `allow-passthrough` and a program that wraps them in `DCS tmux;`. vtmux today registers no notification effect.
- **Ghostty evidence:** inside, OSC 9 (osc/parsers/osc9.zig, which separates out ConEmu) and 777 become `show_desktop_notification`, which reaches the `desktop_notification` effect (stream_terminal.zig:179, 780, 916). The vendored Rust wrapper has no callback for it yet: adding one is a `VENDOR.md` change. As the outer terminal: termio/stream_handler.zig:350, `desktop-notifications = true` (config/Config.zig:3896).
- **Not yet:** OSC 99 (kitty): libghostty parses it but doesn't implement it (stream.zig:3017), and the outer Ghostty doesn't show it.
- **Live upgrade:** nothing to keep. A notification in flight at the exec may be lost.
- **Tests:** an oracle scenario, off: a pane writes OSC 9 and 777, and the screen matches tmux's. An attach test shows the client's bytes carry no notification. With it on: a Ghostty client gets both for a pane in a background window. A client of another terminal and a control client get nothing. `9;4` and the ConEmu forms are not notifications. A flood is cut to the limits above. Passthrough is unchanged.

#### D31: in-band resize (mode 2048)

- **Option:** `vtmux-inband-resize off|on`, server, default off. Rule 4 decides it: only programs that query the mode see it, but neovim stops handling `SIGWINCH` once DECRQM says 2048 is supported (survey section 2.4). So a resize path that misses the report draws the owner's editor at the old size, and default off is how such a path gets found.
- **Behaviour (on):** a pane is granted when its program sets `?2048h` while the option is on. vtmux writes a report at once, then `CSI 48;rows;cols;hpx;wpx t` after every size change of the pane, once its pty winsize is set. A size change is any of these: a layout change, zoom, `resize-window`, a client resize, a swap, join or break across sizes, a respawn, a resume after a live upgrade. The pixel fields come from vtmux's XTWINOPS 14/16 model (`PaneTerm::size_report`; D-014). DECRQM `?2048` answers 1 when granted, 2 when the option is on and the pane is not granted, and 0 (tmux's answer) when it is off and not granted. The grant ends at `?2048l`, RIS (Ghostty's `fullReset` resets the mode too) or a respawn, whatever the option says; a respawned program is granted afresh by its own `?2048h`, which reports the size at once. A report goes only when the pty's size changed, as `SIGWINCH` does. Popups are not panes: they keep tmux's behaviour. (Implemented 2026-11-09: vtmux keeps the mode itself, `?2048` never reaches Ghostty, and writes the report in `Pane::send_size` right after `TIOCSWINSZ`.)
- **Off:** DECRQM 0 and no reports, as in tmux.
- **tmux 3.8:** DECRQM's private table (input_csi_dispatch, input.c:1651-1722) has no 2048, so it answers 0. `input_csi_dispatch_sm_private` (input.c:2022) ignores it. Programs get only `SIGWINCH`. vtmux today drops Ghostty's report (`replies_tmux_does_not_send_are_dropped`).
- **Ghostty evidence:** inside, mode `in_band_size_reports = 2048` (modes.zig:406). Setting it reports at once (stream_terminal.zig:2054, `reportMode2048` :1881-1890). A resize reports through `size_report.encode(.mode_2048)` (`Handler.resize`, stream_terminal.zig:523-551; Rust `Terminal::on_size`, terminal.rs:1722). As the outer terminal: termio/stream_handler.zig:761, termio/Termio.zig:556.
- **Live upgrade:** the grant is a new field of the pane's terminal state (`TermState.inband_resize`, tag 42), required while some program holds it (`requires` names `inband-resize-grant`; rule 6: an ordinary session never produces it, the option being off by default). A build without D31 would drop the grant and send no report, and the program, which stopped handling `SIGWINCH` once granted (neovim 0.12), would draw at the old size, worse than tmux, which never grants it. So a downgrade is refused while a program holds the grant, naming its panes (`a program relies on in-band resize in %N: ...`), and goes through once the program turns mode 2048 off or exits; with no grant, the option on or off, nothing is required (2026-11-09, d31_inband_resize review). A checkpoint (`vtmux-persist`) drops the grant: a restored pane is dead. Ghostty's own mode bit is never set (the set does not reach it). A size queued at the snapshot is reported once the new image sends it, and a client resized during the upgrade is reported once, whichever image sees it.
- **Tests:** an oracle scenario, off: DECRQM, `?2048h`, then a resize, and the pane's bytes match tmux's. With it on: DECRQM 2, then 1; a report at `?2048h`; one report per path in the list above, each checked, so a missed path fails; `?2048l` stops them; turning the option off keeps a granted pane's reports; a set while off stays ungranted after it is turned on; an upgrade onto a build that lacks the grant is refused while a program holds it and goes through after `?2048l` or the program's exit.

#### D33: kitty graphics

Owner, 2026-11-10 ("we are changing our stance around images"). Kitty graphics only; sixel still fails rule 1.

- **Options:** `vtmux-graphics off|on`, server, default off. `vtmux-graphics-limit <MB>`, server, default 256 (10^6 bytes, as Ghostty counts): the image memory of the whole server, every pane and screen together. Ghostty's `image-storage-limit` is 320 MB per screen, primary and alternate each (Config.zig:2515-2522), so one Ghostty window of four splits may hold 2.5 GB. A vtmux server runs for weeks with detached sessions and the outer terminal keeps its own copies, so it gets one cap, just under what Ghostty gives one screen: 7 full-screen 4K RGBA images, or about 80 yazi previews at 1000x800. Lowering it evicts at once.
- **Pane side (on):** a pane screen is granted at its first `APC G` while the option is on. A granted screen gets a storage limit (vtmux sets 0 today, term.rs:576; `Terminal::set_kitty_image_storage_limit`, graphics.rs:279), so libghostty stores its images and placements (`execute`, graphics_exec.zig:25; graphics_storage.zig), and Ghostty's replies (`OK` and errors, honouring `q`) reach the program instead of being dropped by `tmux_reply`. Media: direct only (`t=d`, the data in the escape). File, temporary-file and shared-memory transmissions are refused for every pane before any path is opened, answered as Ghostty answers a medium it does not allow (`EINVAL: unsupported medium`, `LoadingImage.init`, graphics_image.zig), whatever the path names: a pane, or a program on another host through ssh, never makes the server open a path, and no reply tells which files exist or their size. No option turns them on (amended 2026-11-10, review: a FIFO path blocked the server loop until a writer came, and the answers told an existing file from a missing one). vtmux installs libghostty's PNG decoder hook (graphics.rs:17-18). The grant ends as D29's does: when the process group that started it is gone, at RIS or at a respawn; then an APC sets the title again. Images outlive the grant (`kitten icat` exits, its picture stays): the screen keeps its storage until Ghostty frees the last image (deleted, evicted, scrolled out of history), RIS or a respawn. Rule 5: turning the option off keeps granted screens granted. Popups are not panes: tmux's behaviour.
- **Memory:** the limit is shared. vtmux sets each screen's limit to what the others leave, and when a load needs more it evicts across the server in Ghostty's order, unused images first, then oldest (`evictImageExcept`, graphics_storage.zig:1823), by lowering the holding screen's limit (`setLimit` evicts, graphics_storage.zig:336-340). Pending loads (chunked, unfinished: `ImageStorage.loading`) count with the images, by the bytes their buffers hold (amended 2026-11-10, review: Ghostty lets one pending load per screen reach 400 MB whatever the limit).
- **Rendering:** only through unicode placeholders (U+10EEEE, graphics_unicode.zig:16), which are cells, so the existing cell compositor does the rest: scrolling, clipping at pane edges, zoom, popups and menus over an image, window switches and copy mode all come from the cell model, with no pixel compositing. A program's own placeholder cells (virtual placements, `U=1`) are pane cells already; vtmux rewrites only their image and placement ids. A direct placement is drawn as placeholder cells over its grid rect (`grid_size`, `viewport_pos`, graphics.rs:552, 586); its pin keeps it with its text, so it scrolls into history and copy mode shows it there. Cells only: sub-cell offsets (`X`, `Y`) are dropped, and a placement below the text (negative `z`) shows only in cells with no text. These cells exist only in client frames: `capture-pane`, copy-mode copies and formats see the pane as tmux would.
- **Client side:** a client that identifies as Ghostty (`#{client_termtype}`, as D30) gets each image its frame shows as its own upload. Pane ids collide across panes, so vtmux numbers each (pane, screen, image, generation) from a range with the high byte set (the third diacritic); the number is the same for every client, so clients with one cell size still share frames (render/share.rs), while each client keeps its own record of what it holds. An upload is written before the first frame that shows it, through the client's normal output path (backpressure applies): pixels as stored, zlib-compressed (`f=32` or `24`, `o=z`), chunked, `q=2` so the terminal never replies, then a virtual placement (`a=p,U=1`) for its cells. An image none of the client's frames shows any more is freed (`a=d,d=I`), and uploaded again when it comes back. At every attach, the re-exec of a live upgrade included, vtmux first frees its whole range (`d=R`, graphics_command.zig:1172), then uploads what is visible. An animated image shows its current frame, uploaded again when it changes.
- **Geometry:** programs size images by the pane's pixel size, from the window's cell size (D-014: the largest client's, resize.c `clients_calculate_size`, given to the pty and to XTWINOPS). D-014 is fixed first and on its own, being tmux's behaviour. A client whose cells differ gets the image scaled to its own cells (the placement covers the same cells) and shares no frames with clients of another cell size.
- **Other clients:** a client of another terminal, or a control client, gets tmux's behaviour: no uploads and nothing for direct placements; a program's own placeholder cells go out as text, as tmux writes them. Another terminal is added only with evidence that it draws placeholders. `allow-passthrough` is unchanged, so a program that wraps its commands for tmux still goes that way (rule 3 keeps `TMUX` and XTVERSION, so apps that wrap when they see tmux keep wrapping: the real-app checks record which send bare commands).
- **Off:** an APC sets the pane title when `allow-set-title` allows it, and nothing replies, as in tmux.
- **tmux 3.8:** `input_exit_apc` (input.c:2794-2809) takes any APC as a title. No graphics: images reach the outer terminal only by `allow-passthrough`.
- **Ghostty evidence:** inside, storage, placements and placeholders (src/terminal/kitty/graphics_*.zig; Rust API in third_party/libghostty-rs/libghostty-vt/src/kitty/graphics.rs: placements :452-720, `is_virtual` :682). As the outer terminal: the full protocol with placeholders (termio/Termio.zig:294-295, 511-512).
- **Live upgrade and restore:** images are dropped, and the snapshot stays image-free. The grant survives: a per-screen field, required while its process group lives (`requires` names `graphics-grant`; rule 6: an ordinary session never produces it, and `an_ordinary_attached_client_requires_no_feature` shows none needed), with its owning group like D29's (ignorable). So a downgrade onto a build without D33 is refused while a granted program runs. A resumed screen has empty storage: the placeholder cells a program wrote stay in the grid and draw nothing until it sends its images again. Apps that redraw do so on their next repaint (yazi on the next preview, image.nvim on redraw); `kitten icat` output in a shell's history is gone. A checkpoint (`vtmux-persist`) drops the grant: a restored pane is dead. The loss is documented in the README and `DIVERGENCES.md`.
- **Implemented 2026-11-10 (d33_graphics), amended where the code had to choose:**
  - *Memory:* eviction across panes goes screen by screen, the screen whose images grew least recently first, Ghostty's order within it (lowering its limit). Ghostty keeps no per-image age vtmux could compare across panes. While a granted pane's output is parsed its active screen (or one that output grants) may load up to the whole cap, so the server can hold up to twice the cap until that read ends. Ghostty takes a limit of 0 as no graphics at all, so a granted screen never gets less than 1 byte.
  - *Pending loads:* a pending load never holds more than its screen's limit (patch 0043): at the chunk past it the load lets go of its data, its later chunks go unanswered and its last one answers `ENOMEM`, as an image over the limit is answered (`addImage`). One command carries at most what the largest limit could store, in base64 (Ghostty's own 65 MiB at most); a longer one is dropped as Ghostty drops one past 65 MiB. Over the cap after a read, the pending loads of the other screens go first, the one that grew least recently first (they show nothing), then images as above, then the reading screen's own pending load. Decoding one finished command (zlib, PNG) may still take up to 400 MB for as long as the command runs (Ghostty's `max_size`, vtmux's PNG decoder's limit).
  - *Geometry:* a client with another cell size gets the same upload and the same virtual placement: its terminal fits the image to the placement's cells (kitty placeholders are drawn fitted to their cells), so nothing is scaled server-side. It still shares no frames with clients of another cell size (the cell size is in the share key while graphics are drawn).
  - *Clients:* a graphics client is a Ghostty one (XTVERSION) whose terminal also writes RGB colours and underline colours: the ids are colours, and a downgraded colour would name another image. A direct placement's cells name a placement id vtmux picks (`0xF00000` and up), so a program's virtual placements keep theirs.
  - *Copy mode:* shows the direct placements taken with its copy, over the copy's rows; a copy reflowed by a resize drops them. A program's own placeholder cells in history are rewritten like any.
  - *Not done:* animation is not driven (Ghostty's `animation_tick` is never called), so an animated image shows the frame it was sent with. A program's placeholder cells for an image vtmux cannot draw go out as blanks to a graphics client.
  - *Real apps:* yazi 26.9.1 sets `allow-passthrough all` on its pane and wraps every command for tmux, on or off; chafa, `kitten icat` and image.nvim are not on the test host. A bare emitter is checked end to end (`docs/test-health/2026-11-10-graphics-real-apps.md`).
- **Tests:** an oracle scenario, off: a pane sends a transmit, a query and a placement, and its title and bytes match tmux's (no reply). A recording client (an attach test keeping a Ghostty client's bytes) checks the escapes: the upload before the frame, the virtual placement, placeholder cells with vtmux's ids and the right row and column diacritics for a direct placement clipped at a pane edge, under a popup, zoomed and in copy mode; the free at a window switch and the upload on return; the range free then uploads at attach and after `vtmux-upgrade`; scaled uploads for a client with another cell size; nothing for another terminal's client or a control client. Units: ids across panes, the shared limit and eviction across panes, pending loads held to it (the oldest other screen's first), file, temporary-file and shared-memory media refused with one answer whatever the path (a FIFO answered at once), the grant's start and end, rule 5, replies only for granted screens. Real apps on Ghostty, recorded in a `docs/test-health/` note: yazi previews, `kitten icat`, `chafa -f kitty`, image.nvim, each with the option off (tmux's result) and on.

## Scope

In (eventually, M2): everything tmux 3.8 does that is observable through the CLI, config, control mode or the attached screen — including floating panes.

Out:
- Native image rendering other than kitty graphics, which is D33 (opt-in). Sixel fails D28's rule 1 (Ghostty has no sixel). Other images work via `allow-passthrough` only.
- Windows. Linux is primary; macOS supported and CI-gated, second.
- tmux's imsg wire protocol. A real `tmux` client cannot attach to a vtmux server.
- iTerm2 `-CC` integration polish beyond tmux's own bytes (plain `-C` is in; `-CC` has tmux's DCS start, `ST` end and raw terminal mode, client.c, control.c).
- Anything only on tmux master after 3.8, until a deliberate target bump.

## Rust at the core, tmux at the edge

The central distinction from tmux-rs and rmux. Compliance is a property of the **edge**; inside it, vtmux is idiomatic Rust with no concessions to tmux's C.

**The edge** is everything an outside observer can see, and it matches tmux 3.8 exactly:
- CLI argv, exit codes and error message text
- config syntax and the command language
- format expansion, option names, scopes and values
- `list-*` / `show-*` output, ordering included
- control-mode protocol, hooks, `$TMUX`, environment, socket paths (D20)
- what the attached client sees on screen

**The core** is everything else, and follows Rust practice, not tmux's structure:
- Types make bad states unrepresentable: newtype IDs (`SessionId`, `WindowId`, `PaneId`), enums for option values and command arguments, no C-style flag ints, no sentinel values.
- Ownership instead of a pointer graph: ID-keyed arenas, borrows checked by the compiler. No `Rc<RefCell<_>>` webs standing in for tmux's pointers.
- Errors are `Result` values, typed per layer, turned into tmux's exact message text only at the edge.
- No global mutable state. The server owns its state; pure functions in `vtmux-core` take what they need.
- Parsers produce typed ASTs (commands, formats, styles, layouts), which are tested and fuzzed independently of the server.
- Traits at the seams that need test doubles (PTY, clock, filesystem), not everywhere.
- Edition 2024, clippy pedantic, `#![forbid(unsafe_code)]` outside D10's two modules.
- Names describe what a thing is in vtmux. tmux's names appear only where they're part of the edge (command, option and format names).

**The trap to avoid:** some tmux behaviour that's visible at the edge is a side effect of its data structures. Examples: `list-sessions` order comes from an RB tree keyed by name, IDs are never reused within a server lifetime, and the command queue order determines when hooks fire. vtmux reproduces each of these **on purpose and visibly** (for example, a `BTreeMap` keyed by name, or a monotonic ID counter), with an oracle scenario pinning it. It never copies tmux's structure to get the ordering for free.

A reviewer rejects a change that leaks tmux's internal shape into the core when the edge doesn't need it.

## Architecture

```
vtmux (bin)      CLI parse → run a command against the server, or attach
├─ vtmux-core    pure, no I/O, no unsafe: command parser, command table, targets,
│                options (scopes, arrays, user options), formats, styles, key tables,
│                layout strings. Most of tmux's semantics live here.
├─ vtmux-vt      the only FFI crate: safe wrapper over libghostty-vt, plus tmux-shaped
│                serialization (capture-pane -p/-e/-J, pane_* values, cursor).
├─ vtmux-server  mio event loop; sessions/windows/panes in ID arenas ($N @N %N);
│                PTYs; job runner; hooks; control-mode clients; compositor
│                (panes + borders + status + popups + floating layer → frame);
│                per-client encoder driven by terminal-features.
└─ vtmux-client  attach: raw tty, forward input bytes, write frames, resize/signals.
```

Runtime: the first command starts a background server at `$TMUX_TMPDIR/vtmux-UID/<label>` (`-L`/`-S` as tmux). Each invocation connects, sends argv/cwd/env/tty info, gets output and an exit code; `attach` keeps the connection open. libghostty's `on_pty_write` callback routes terminal query replies (DA, DSR, …) back into the pane's PTY.

## Compliance: triangulation

Three independent sources of truth:

| Source | Tells us | Authoritative for |
|---|---|---|
| tmux 3.8 `regress/` | what tmux is meant to do | intent and chosen edge cases |
| Behaviour oracle | what tmux 3.8 actually does | everything observable via CLI, control mode, attached screen |
| esctest / specs | what a correct terminal does | the pane grid (D4) |

### Regress harness

```
compat/
  tmux-3.8/regress/   vendored verbatim from tag 3.8, never edited
  patches/            one minimal patch per divergent assertion
  expected.toml       per test: pass | xfail(reason, link) | skip(out-of-scope)
  DIVERGENCES.md      D-NNN: test/assertion, tmux behaviour, vtmux behaviour, evidence
```

`cargo xtask regress`: copy suite to a temp dir, apply patches, run each test with `TEST_TMUX=target/debug/vtmux` under `env -i` (as tmux's Makefile does), in parallel. Fails on unexpected failures **and** unexpected passes. Prints a scoreboard and writes JSON for trend tracking. `--update` only records fail→pass flips; adding an xfail is a manual, reviewed edit.

At tag 3.8 the suite has 174 tests; 84 need an attached client or control mode. Tests from tmux master may run on a separate, non-gating "preview" scoreboard.

### Behaviour oracle

```
oracle/
  scenarios/   declarative: setup, steps (CLI commands, keys via attached client,
               bytes into a pane, resizes, sync points), observations
  traces/      golden traces recorded from real tmux 3.8, committed, tagged with tmux version
  harvest/     gitignored raw logs from the harvest shim
```

`cargo xtask oracle` modes:
- `record` — run scenarios against pinned tmux 3.8, write normalized traces.
- `replay` — run the same inputs against vtmux and diff against traces. No tmux needed; this is what CI runs.
- `live` — record and replay side by side, nothing saved; for exploration and bisecting.
- `harvest` — turn logs from an opt-in logging `tmux` shim (real invocations from plugins, murmur, mu) into candidate scenarios.

Observations: CLI stdout/stderr/exit code; ordered control-mode notification stream; format/option queries; **the attached client's screen**, obtained by running the multiplexer attached in a PTY and feeding its output into a libghostty-vt observer terminal, then comparing the resulting grid — not the raw escape bytes, which legitimately differ.

Sync: wait for quiescence (no PTY output and no pending jobs for N ms) plus `wait-for` channels where possible. No fixed sleeps.

Normalization: pids, socket paths, timestamps, tty names and similar volatile values are rewritten to placeholders before diffing.

A trace step may carry `divergence = "D-NNN"`; replay then expects vtmux's behaviour for that step.

Corpus growth: a scenario with every feature and every bug fix; harvested real-world patterns; generated cases from tmux's `fuzz/*.dict` and from the owner's config formats. Bumping past 3.8 = re-record all traces; the trace diff is a precise changelog of tmux behaviour changes.

Privacy: harvested logs stay local; a scenario is committed only after manual review with paths and contents replaced by synthetic ones.

### Fuzzing

`cargo-fuzz` targets per core parser (commands, formats, styles, layouts), seeded from tmux's dictionaries. Nightly, not per PR.

### CI (GitHub Actions)

Per PR, Linux: fmt, clippy pedantic, unit tests, `xtask regress`, `xtask oracle replay`. macOS: same minus fuzzing, required. Scoreboard posted on the PR. Real tmux 3.8 is built from the tag and cached (used by `record`/`live`; locally via `$VTMUX_REFERENCE_TMUX`, else built).

### Divergence process

1. Regress or oracle mismatch.
2. Classify: (a) vtmux bug → fix; (b) grid-level difference → run the D4 arbiter; (c) libghostty bug → patch, log, upstream.
3. If (b) and Ghostty wins → `D-NNN` in `DIVERGENCES.md` with evidence, plus a regress patch or trace annotation. No verdict → match tmux.

Each `D-NNN` carries a category, borrowed from rmux: `Ghostty grid` (D4 arbiter ruled), `Do not copy tmux bug` (tmux loses data, hangs or is unsafe; needs evidence and a regression test), `Deferred` (not done yet; must not be claimed as compatible), `Spec decision` (a numbered decision here, such as D5's `tmux` shim, chose it for drop-in use), or `Extension (D28)` (a protocol tmux drops, behind its `vtmux-*` option, seen only by a program that asks; it names the option and the oracle scenario that pins it off). There is no `Intentional divergence` category for product reasons. vtmux's only surface beyond tmux's is its opt-in paper cuts and D28 extensions.

## Milestones

**M0 — walking skeleton.** Server, one session, one pane on libghostty-vt, `attach`/detach, `-C` control mode, `display-message -p`, `capture-pane -p`, end to end and thin. Harness and oracle `record`/`replay` running against it. (Half the 3.8 suite needs attach or control mode, so these come first.)

**M1 — daily driver.** During the daily-driver week real tmux stays installed but does not own the default `tmux-UID` server (D20); the oracle runs real tmux under its own `TMUX_TMPDIR`. The owner's unmodified `.tmux.conf`, `mu-crew.conf`, TPM plugins, murmur and mu work, with `tmux` symlinked to vtmux. Surface, derived from what these actually call:
