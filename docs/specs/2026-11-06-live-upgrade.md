# Live upgrade (persistence removed)

**Status (owner, 2026-11-12, M5):** phase 3, persistence (checkpoints on disk, the restore at server start, restored panes), is removed: restoring sessions after a crash or reboot is tmux-resurrect's job, and vtmux keeps only what tmux and its plugins can't do (live upgrade, new terminal protocols, pane blend). Phases 1 and 2 (snapshot, live upgrade) stand unchanged. The removed decisions and sections stay below as history, each marked; *Removal* lists what went and what live upgrade keeps. 3.8-beta1 to 3.8-beta3 shipped persistence and stay as released.

## Problem

Moving a running vtmux server onto a new binary means `kill-server`: every pane's process dies. The owner hit this on 2026-11-06: the dogfood binary spoke protocol 8, the running server 7, so a client of the new binary could not even talk to the old server (`protocol version mismatch`), and the only way forward was to lose every shell, agent and build. vtmux ships several times a day; each dogfood build costs a full restart.

tmux has the same defect: upgrading tmux while a server runs ends in the same mismatch error, and the advice is to kill the server (tmux FAQ, "protocol version mismatch"). The tmux answer to losing state, tmux-resurrect and tmux-continuum, saves layout, working directories and a guess at each pane's command, and at best plain-text scrollback scraped through `capture-pane`, and restores after the processes are gone.

vtmux owns every pane's grid (libghostty-vt) and its server is one process that owns every pane's pty and child. It can do better than both: replace its own binary without the panes noticing, and, from the same serialized state, restore sessions with their exact screens after a crash or reboot.

## Approach

One mechanism, three phases built in order:

1. **Snapshot.** A versioned, stable encoding of the whole server state: sessions, windows, layouts, panes, options, environment, hooks, key tables, buffers, clients' attachments, control-client state, and every pane's terminal state (screen, history, cursor, modes, the tmux row flags) cell for cell.
2. **Live upgrade.** `vtmux-upgrade` makes the server write a snapshot, check that the new binary can read it, and replace itself with that binary in the same process (`execve`), keeping the listening socket, every client connection, every pane and popup pty and every `pipe-pane` descriptor open. The new image reads the snapshot and carries on. Pane processes never notice; attached clients re-exec themselves onto the new binary and redraw; control clients stay connected without noticing.
3. **Persistence.** **Removed 2026-11-12 (M5): restoring is tmux-resurrect's job.** With `vtmux-persist` on, the same snapshot is checkpointed to disk. A server that starts and finds one for its socket restores it: sessions, windows and layout come back, panes come back dead with their last screen and history, and `respawn-pane` restarts them. Nothing can bring processes back after a reboot; this restores everything else.

Live upgrade is the motivation and qualifies as a fix (feature policy, *Paper-cut fixes*): it fixes a defect in something tmux already does (upgrading loses sessions), it is invisible to scripts (the server keeps its pid, socket, sessions and ids), it has a source (the tmux FAQ entry and the 2026-11-06 restart), and it gets a PAPERCUTS row. Persistence was a new capability, so it was opt-in (`vtmux-persist`, default `off`) and amended the non-goals (restoring state allowed, launching commands to recreate it out, except the opt-in restart of default shells, decision 32); removed 2026-11-12 (M5): restoring is tmux-resurrect's job, and the non-goal is whole again. This is D27.

## Removal (2026-11-12, M5)

Owner decision: vtmux keeps only what tmux and its plugins can't do (live upgrade, new terminal protocols, pane blend); restores across reboots are tmux-resurrect's job. A hard removal: no deprecation shim, no option kept as a no-op (the owner is the only user). 3.8-beta1 to beta3 stay as released.

**Goes.**

- Options `vtmux-persist`, `vtmux-persist-respawn`, `vtmux-persist-drop` (`vtmux-core/src/options/vtmux.rs`, their golden tests in `options/golden.rs`). A config still setting one gets tmux's unknown-option error, as for any option vtmux lacks.
- The disk checkpoint: `vtmux-server/src/persist.rs` (directory, `lock`, `manifest`/`manifest.prev`, `chunks/`, GC, flushes) and `server/persist.rs` (the 60 s timer, the shutdown and last-session checkpoints, the lock's hold, `vtmux-persist off` recorded on disk), with `persist/tests.rs` and `server/persist/tests.rs`; the event loop's hooks into them in `server.rs` (`persist` field, `persist_timers`, `persist_deadline`, `checkpoint_exit`).
- The cold restore at server start: `server/restore.rs` (the config pre-read of the persist options, the dry run of a checkpoint, the import, the dead line of a restored pane, `vtmux-persist-drop`) and the config-on-top rule only it used (`Server::config_sets`, `SetOption::config_sets`, the options helper reading the startup config's sets), with `restore/tests.rs`; `restore::start` in `server.rs` becomes the plain start it was before.
- Restored panes: `restored.rs` (the hint over the bottom row, Enter as respawn, the respawn that keeps the screen above a marker, `auto`'s pass, the restart guard), with `restore/respawn_tests.rs`; their hooks in `server.rs` (respawn branch, `refresh_restored_hints`, the auto pass, the guard on exit), `key_dispatch.rs` (`restored_enter`), `render/window.rs` (the hint), `remain.rs` (`keep_restored`, `draw_restored_dead_line`, the `remain-on-exit key` bypass), `model.rs` (`Pane::restored_from`, `restored_hint`, `restart_guard`); in `vtmux-vt`, `RowCopy`, `PaneTerm::copy_rows` and `put_rows`, which only that respawn used (the Ghostty patches stay: changing the patch stack would send every upgrade from beta3 through rows, decision 23).
- In the server's snapshot code: exporting a checkpoint (`Purpose::CheckpointLayout`/`CheckpointFull`, the screenless export a `layout` checkpoint took); `resume.rs`'s branch that checked a checkpoint for a starting server.
- In `vtmux-snapshot`: `encode_manifest`, `decode_with`'s chunk fetcher (pages are always inline now), `page_refs`, and their tests.
- `cargo xtask reap`'s checkpoint-directory sweep (`sweep_checkpoints`, the lock taken to empty one, `default_state_root`, `Held::may_own`, `bound_now`, their tests); socket and process reaping stay as they are.
- Tests: `crates/vtmux/tests/persist.rs` whole; checkpoint round trips in `vtmux-server/tests/snapshot_term.rs` become row-form upgrade streams (`Form::Rows`, the path an upgrade across patch stacks takes) so the reflow and hidden-history cases stay covered; the persist round of `scripts/chaos_upgrade.py` (`--persist-every`). No oracle scenario uses persistence, so none goes.
- Docs: README's *Full restores* (its *What tmux can't do* becomes live upgrades, terminal features, pane blend), PAPERCUTS' restore row and three option rows, ARCHITECTURE's *Persistence* and the crate table's mentions, PERFORMANCE's checkpoint paragraph, the D33 README note on restore, AGENTS.md's checkpoint-dir sweep; CHANGELOG gets an *Unreleased* entry saying it went and that `~/.local/state/vtmux/` can be deleted. Release notes and `docs/test-health/` records are history and stay.

**Stays, because live upgrade needs it.**

- The snapshot format whole: every record, tag and migration, the `v1.snap` golden file (never edited after release), `Form::Rows` (upgrades onto another patch stack, decision 23), the inline page hashes, and `Error::MissingChunk` with `hex` (a page without its bytes).
- The fields only checkpoints set (`Server::persist_hold`, `Pane::restored_from`, `Pane::restart_from`) and the `Purpose` values 1 and 2: still decoded, since a 3.8-beta3 image's upgrade stream may carry them, and never written. `persist_hold` is a `one` field, so it goes out as 0, which is "free", what a beta3 reader assumes; the other two are `opt` and absent. The reader ignores them: a pane a beta3 server restored comes over as an ordinary dead pane with its saved screen (status unknown, `JobStatus::Unknown` stays for it), and `respawn-pane` respawns it as tmux's does; a respawned one's guard is dropped, so its program's exit is any pane's. That is the known limit beta2 already had for beta3's restored panes (decision 31's *Provenance*). A checkpoint (purpose other than `Upgrade`) given to `--vtmux-check-snapshot` is refused: only a beta3 server's own restore ran it on one, with its own binary.
- An option of the old image this build lacks (`vtmux-persist` and friends after an upgrade from beta3) is dropped on import, the `@` user options excepted: an array of strings would otherwise land in the tree under a name no command knows.
- The dry run (`--vtmux-check-snapshot`), its acknowledgement line and the `-V` fallback (decision 6), the resume, the switch back, the last resorts (part by part, then without terminal state) and the readers of a pane without terminal state; `restore_term`; `PaneCompress::restored` and `Alerts::restored` (named for an upgrade's import, not for persistence).
- Live upgrade both ways with 3.8-beta3: downgrade onto it (its image finds no `vtmux-persist`, so it stays off and writes nothing) and upgrade from it (the fields above read and ignored).

## Design

### Snapshot (phase 1)

The snapshot module (new crate `vtmux-snapshot`, `#![forbid(unsafe_code)]`) owns the format: record types, encoder, decoder, version migrations. It does not depend on `vtmux-server`; the server converts its model to and from snapshot types.

What it carries, at minimum:

- **Server:** server options, global session/window/pane options, environment, hooks, key tables and bindings, aliases, paste buffers (with names and order), message log, id counters (`$`, `@`, `%`, client), the start time, prompt history, wait-for channels' state.
- **Sessions, windows, panes:** every field the formats and commands can observe (names, ids, indexes, flags, groups, last/active stacks, layout tree, zoom, floating panes, modal panes, marked pane, synchronize, `remain-on-exit` state, dead status and exit info, titles, cwd, the start command (tmux keeps no per-pane environment: `struct window_pane` has none, so neither does the snapshot), pane pid, the tty name, alert flags, activity/silence timestamps, pipe-pane state).
- **Pane terminal state:** the primary and alternate screens and history, cell for cell, in the vtmux row/cell format: text (graphemes), width, every attribute and colour (including the 256-colour form of palette 0-15), hyperlinks, the tmux row flags (wrapped, cells-used, prompt marks), cursor (position, shape, visibility, pending wrap, saved cursor), modes (DEC private and ANSI modes, mouse, keyboard protocols, bracketed paste, focus, sync hold), charsets, tab stops, scroll region, title stack, palette overrides, colour replies held, and the compression state of history pages.
- **Clients:** each attached client's session/window, flags, size, terminal features, key table, prefix state, read-only/ignore-size flags, and control clients' subscriptions, pause-after, paused panes, output offsets and flags.
- **Modes in progress:** copy mode, tree modes, view mode, prompts, menus and popups. Copy mode keeps its frozen grid (it is a snapshot of the pane by D-010) and position; tree modes, menus and prompts may be closed by the upgrade instead (the user re-opens them) if carrying them is costly: the builder decides per mode and records it.

The exact field list is the builder's job, driven by one rule: after a self-upgrade, every format variable, every `show-*`/`list-*` output and every client screen is byte-identical (decision 13). An oracle step type `upgrade` (see Tests) enforces it.

**Required and ignorable fields.** Within a format version a field added later is either ignorable (an older reader skips its tag) or required (the writer names a feature in the snapshot's `requires` list and a reader lacking it refuses the stream, so the dry run fails and the old server keeps running, decision 6). A field is required only if losing it loses session state and an ordinary session does not produce it; what nearly every attached client has (where its terminal's queries stand, the title its terminal shows) is ignorable, so a downgrade to the build before works with clients attached: the older image starts their decoders afresh and shows the next title set (revised 2026-11-07 after review_upgrade_every_fixes, `high_downgrade_required_features`; `an_ordinary_attached_client_requires_no_feature` pins it). State an ordinary session produces in a new form is written beside what the build before reads for it, in the fields that build reads: a primary screen the alternate one left at its size (a pane resized under vim) also goes at the pane's size, reflowed as the old emulator kept it, and `?1049h`'s save also goes in the primary screen's DECSC slot, where the old `?1049l` restores from; a reader of the new fields takes them and gives the slot its own value back (2026-11-08, `low_alt_screen_47_1047`; `a_primary_screen_left_at_its_size_requires_nothing`, `an_older_reader_takes_the_screens_it_knows`, `an_older_writers_1049_save_is_kept`). So are tmux's line flags a row keeps where its cells no longer say so (Ghostty patch 0034: `echo café` and two backspaces in bash): they go beside the rows under their own tags, the row codec unchanged, and the build before, which skips the tags, derives the flags from the cells as its build always held them (2026-11-08, regress_xfail_d027 review: a `requires` entry blocked a downgrade to main from nearly every session; `kept_line_flags_require_nothing`, `kept_line_flags_round_trip_and_require_nothing`). So is the history an alternate screen shows, which a build with Ghostty patch 0038 reads in place in the primary screen: a stream of rows (a checkpoint, an upgrade onto another patch stack) also carries the copy the build before took on `?1049h`, the newest `hsize` primary rows at the width the primary was left at, its whole pages the primary's own; the reader of the patch takes the primary's rows, and a same-stack upgrade carries no copy (2026-11-10, perf_alt_screen_history review: without it main showed no history under vim after a downgrade and ignored a history-limit lowered there; `an_older_reader_gets_its_copy_of_the_hidden_history`, `a_downgrade_under_an_editor_keeps_the_history_it_hides` against a build of main).

**Ghostty access.** Encoding and decoding a pane's terminal state needs a libghostty-vt export/import API: rows with cells, styles and row flags, plus terminal state Ghostty owns (modes, charsets, tab stops, saved cursor). That is a new vendored patch, scoped to reading and writing that state through public functions, never by copying Ghostty's internal layout (decision 11). History pages that are LZ4-compressed in memory are exported compressed when their content is already in the row format the snapshot uses; otherwise they are decoded and re-encoded. An import validates every part of the state before Ghostty sees it (counts, indexes, widths, cursor and region bounds, page widths equal to the terminal's) and refuses a malformed one with an error, never a later crash; a compressed-page blob carries a checksum over its bytes, which every import (the dry run's too) checks with the blob's `Page` value against its capacity's layout before it reads either; the LZ4 bytes are decoded on the page's first read (revised 2026-11-07, `lu_upgrade_perf`: a dry run that decoded every blob would cost what decoding all compressed history costs, the thing decision 23 avoids, and a blob whose checksum holds is the bytes the writer's Ghostty exported, inside a stream whose BLAKE3 hash holds too; the code never did decode them in the dry run). Pages stream one at a time (`export_pages`, `StateImport`), so the encoder never holds a pane's whole history in the row format.

**Spike first.** The first unit proves the Ghostty export/import on one pane with history (round-trip byte-identical `capture-pane -e -S -` and screen) and measures it at 100k lines. If the patch turns out too invasive, the fallback (decision 5) is replay through escape sequences plus a side channel for the row flags and modes replay cannot express; that is an orchestrator escalation, not a builder choice.

### Live upgrade (phase 2)

**Handshake.** A new frame type, `UpgradeRequest { binary: path }`, is recognized before the protocol version check and documented as frozen: its encoding never changes. A client of any newer binary sends it to a server of any binary that has the feature. The server answers with a frozen `UpgradeResult { ok, message }`. `binary` is an absolute path (the server's working directory is not the requester's), and a peer the access list (`server-access`) denies or makes read-only is answered `access denied`: the request runs a binary as the server's owner. The `UpgradeNotice` token is `[A-Za-z0-9]{16,64}` and its binary absolute; clients refuse a notice that breaks either rule, since the binary goes on the re-executed client's command line and the token in its environment. Everything else stays version-checked. The rest of the frozen contract (`vtmux-core::protocol`, *Frozen frames*): `MAX_FRAME` (16 MiB); `Hello`'s version right after the tag, read before the rest, so a `Hello` of another version that does not decode still gets the mismatch; `Hello`'s trailing extension area, where later versions add fields; clients skip server frames with tags they don't know. No frozen frame reports the server's version: a control client learns it only with `display -p '#{version}'`.

**Command.** `vtmux-upgrade [-b binary]` is a server command (bindable; `tmux vtmux-upgrade` from a shell). From the CLI, a client whose version differs from the server's sends the frozen `UpgradeRequest` instead of the normal command path. `-b` defaults as decision 22 says (the server's own start path, re-resolved at request time). The protocol-mismatch error adds: `run 'tmux vtmux-upgrade' to move the server onto this binary`.

**Sequence (server):**

1. **Preflight:** refuse with a message if `run-shell` / `if-shell` jobs are still pending after waiting up to 3 s, if the binary is missing or not executable, or if another upgrade is running, and at once if work is queued behind the requester in its own queue (`vtmux-upgrade ; set ...`, the rest of a sourced file): no queue crosses the `execve`, so it would never run (2026-11-10, `panel_g1_upgrade_losses`). Keys alone behind it (typed right after a key bound to `vtmux-upgrade`) have run nothing, so they are not refused: they go back to the client's input as the bytes they came in, which the snapshot carries (`inbuf`) and the image that serves next reads once the client has re-attached; an upgrade that ends without an exec reads them at once (`lows_batch_m3`). Each goes back as its own frame and is decoded again as the key it was, its `escape-time` wait out, and the bytes the decoder held behind them keep the instant their wait started, carried as an age (the client record's `given_back_keys`, `given_back_held`, `held_ago_ms`); so does an open bracketed paste (`pasting`), which goes on after the re-attach. A paste typed behind the key goes back too, its marks as the bytes `\e[200~` and `\e[201~` they always come from (tty-keys.c `tty_keys_next`), the decoder's paste set back to the client's so they are decoded again; only a mouse event or a `send-keys -K` key, whose bytes are not kept, still refuses (2026-11-11, `final_fix_upgcheck`: a paste in the same read as the key refused the upgrade). A key's time is when the server read its bytes, and bytes read join what the decoder holds whether or not its wait is out, as in tmux, whose read callbacks run before the key timer they find expired (libevent; tty-keys.c `tty_keys_next` takes an ESC and an `x` in its buffer as M-x, timer out or not), so a loop busy past `escape-time` reads an ESC and a late `x` as M-x (revised 2026-11-11, `final_fix_misc`: the read had decoded the expired ESC alone first). Escape then `x` typed during a key-bound upgrade stays Escape and `x`: the keys given back are decoded at their own instants, and the held ESC's wait runs out in the image holding it, which fires it before the client is back to send the `x` (2026-11-12, `panel_fix_upgrade`; all four fields ignorable: a build before reads the frames as bytes read at once and ends the paste, as it always did).
2. **Quiesce:** stop reading pane ptys and client sockets (data stays in the kernel buffers; pane programs block briefly, nothing is lost); flush pending client output. The state is frozen only while a snapshot is taken (step 3), not through the dry run (step 4).
3. **Snapshot** into an anonymous memory file (decision 19).
4. **Dry run:** fork and exec `<binary> --vtmux-check-snapshot <fd>`. The child decodes the snapshot fully, verifies it, rebuilds the server from it, writes on stderr the line `vtmux-snapshot-checked <hex>` (the BLAKE3 hash of the body that the stream's header records and the decode checked) and exits 0, or non-zero with a message. It passes only with that exact line for the stream it was given: an exit status of 0 alone is any program's (`/bin/echo`, `true`, a script), and the exec that followed replaced the server with it, every session gone (2026-11-11, `final_fix_upgcheck`, from the macOS end-to-end review). A vtmux from before the line writes none; so that a downgrade onto one stays the rollback for a dogfood build (decision 6), a dry run that exits 0 without the line passes only if `<binary> -V`, run as `vtmux` (`argv[0]`, so a binary installed as `tmux` answers as vtmux), prints exactly `vtmux 3.8-beta1` or `vtmux 3.8-beta2` and a newline within 1 s: the releases before the line, and this cycle's builds before it, which report 3.8-beta2 (orchestrator, 2026-11-11). `/bin/echo -V` prints `-V`, a script nothing, so they stay refused; a program that lies about its version is not guarded against. The `-V` runs only for a binary that does not acknowledge, holding the loop at most that second. The same goes for a switch back by path (macOS) onto such a build. The image leaves the file at offset 0 for a dry run that reads its descriptor, as a test's script does. It may take 3 s, and a second more for each 100k rows of history it imports in the row format (`lu_upgrade_perf`: a fixed 3 s refused every upgrade of 10 x 100k uncompressed lines for its size), after which it is killed and the upgrade refused. The server serves on while it runs (panes, clients, commands; only the requester waits), polling the child from its loop; its reaping of children leaves the dry run's to the dry run, which kills the child's process group before reaping it. On failure, report the message to the requester; the old server keeps running. Once it passes, the snapshot the exec carries is taken again: the preflight's wait for work in flight once more (the server ran on, so a job or command may have started), then the quiesce and the snapshot (steps 2 and 3), so what changed while the dry run ran is carried, not lost. The dry run has shown that the binary reads this server's snapshots; the content since is new to it, and a failure reading that after the exec is decision 7's switch back. A snapshot that requires a feature the checked one did not (a pane's first history page in Ghostty's form, from a pane printing through the dry run; a very visible cursor; an auto-hide scrollbar shown; a program granted mode 2048, D31) gets a dry run of its own, and so on, at most six dry runs in all (there are five such features: revised 2026-11-11, the graphics grant made the fifth), then the upgrade is refused: the binary was never shown it can read it. (Revised 2026-11-07, `lows_batch_j` after review_upgrade_cmd_2: a dry run that held the loop froze every pane and client for up to its limit; re-snapshotting rather than refusing on change, since under load the state always changes.)
5. **Prepare descriptors:** clear close-on-exec on the listening socket, every client socket, every pane/popup pty master, every `pipe-pane` descriptor and the snapshot file; record their numbers in the snapshot's descriptor table. Everything else (signal pipe, `#()` job pipes, timers) is recreated by the new image.
6. **Notify clients:** send attached clients the frozen `UpgradeNotice { binary }` and keep their sockets open. Control clients get nothing.
7. **Exec:** `execve(<binary>, [<binary>, "--vtmux-resume", <fd>], env)` (`argv[0]` is the path exec'd, made absolute from the requester's directory and cleaned lexically (no `.` or `..` component; a symlink is kept as given, so its path shows in `argv[0]` and `comm` while `/proc/<pid>/exe` and the shim name its target), so `ps`, `pkill -f` and plugins name the image that runs, not the one before it; a switch back to the kept executable uses the path the snapshot names for it), with `-S <socket>` after `argv[0]` when the binary's dry run said on stderr that it takes it, so `ps` still tells which server it is (the oracle runner and `cargo xtask reap` go by the `-S` socket and `--vtmux-resume`, whatever `argv[0]` is called); a binary from before that parses only the bare form, and a switch back passes on the `-S` the failing image was given. On `execve` failure (returns), restore close-on-exec, resume and report.

**Sequence (new image):** `--vtmux-resume <fd>` decodes the snapshot, adopts the descriptors by number, rebuilds the model and pane terminals, reaps any child that exited during the exec (`waitpid(-1, WNOHANG)` matched to pane pids), re-runs `#()` jobs, re-arms timers, then resumes reading ptys and sockets and redraws every client. If decoding or adoption fails here (an error or a panic), it execs the previous binary with the same descriptors and snapshot (decision 7): the executable that image kept open since it started (Linux `fexecve`; the snapshot's header records its descriptor), so a relink or a binary from before this feature installed at its path meanwhile does not matter; where there is no `fexecve` (macOS), its path, only after a dry run of it passes. If that fails too, it serves the panes with no history rather than exit, and if even that fails it serves with no session on the listening socket while holding every pane pty open and reading it, its output discarded so no program blocks on a full terminal (`show-messages` says why, `kill-server` releases them): panes never die because of an upgrade. The last resort but one goes part by part: it first rebuilds the server without only the parts that do not read (a pane's or popup's terminal state, or a copy mode, holding a page that does not check or a terminal state that does not import), every other pane keeping its screen and history; only when that rebuild fails too does it drop every pane's terminal state. A stream that decodes but fails the new image's check (a record that does not check: a page past the reader's limits, which every vtmux before 8c94c6e wrote for a copy mode over more than 65536 rows of history entered while the dry run ran) gets those last resorts in the new image at once, the part-by-part rebuild and then the one without any terminal state, and is switched back for only if both fail: the image that wrote it can do no better (one before a548110 serves no session at all), and the switch back is kept for what this image cannot keep the panes of at all. The answer (still an error on the wire and in a control client, so a script sees that something was lost; a command client exits 2, not the 1 of an upgrade that did not happen, decision 7; the frozen `UpgradeResult` has no field for it, so it is `ok` false with a message starting `live upgrade took effect`, which the requester reads) and `show-messages` say the upgrade took effect without each part left out (`live upgrade took effect without %1's copy mode: <why>`, or `without the panes' terminal state`), where an image switched back to says `live upgrade failed: ...`; a dry run that refuses a copy or view mode (open when the upgrade starts) says to leave each such mode and upgrade again (`leave copy mode in %1 and view mode in %3 and run vtmux-upgrade again`), whatever part comes first (revised 2026-11-08 after the chaos driver's review and its re-review, `lu_switchback_last_resort`). A switch back and a rebuild without terminal state are logged in `show-messages` too, with why (the failing image passes it to the one it switches back to in `VTMUX_UPGRADE_FAILED`, not as an argument an older image could not parse); the requester learns it from `vtmux-upgrade`'s result, which only the image that ends up serving sends: the snapshot names the requester (its client, or the handshake's connection, kept open across the exec), so a command client exits 0 only once the new image runs, and a failure before the exec (the dry run, an `execve` that returns) is reported by the old image (revised 2026-11-07 after review_lu_upgrade_cmd: answering when the dry run passed reported a failed exec as success). The signals the server handles are blocked from just before `execve` until the new image has its handlers, so none arriving in between kills the process; the dry run rebuilds the whole server on placeholder descriptors, not only decodes the snapshot; and the listener and pty masters are close-on-exec from creation, cleared only for the `execve` that keeps them.

**Clients.** On `UpgradeNotice { binary, token }`, an attached client execs `<binary>` with its original arguments rewritten to a re-attach carrying the token, on the same tty, reconnecting through the same socket path. The new server rebinds it to its old client record (decision 21): same id, session, flags, key table and creation time, no attach/detach hooks or notifications. Its terminal is re-initialised as at any attach and fully redrawn. A client binary from before this feature ignores the notice; the new server detaches it with `[server upgraded: re-attach]`.

How (`lu_client_reexec`, orchestrator's builder): a client says in its `Hello`'s extension area that it follows upgrades (`HelloExt::follows_upgrade`), so the old image knows which clients a notice reaches: only those get a token (the snapshot's client record carries it) and the notice, sent once the dry run passes; the others are what decision 25 detaches and names, in the image that serves next. The re-attach command line `<binary> --vtmux-reattach <socket path>` (`argv[0]` kept), with the token in the environment variable `VTMUX_REATTACH_TOKEN` (not on the command line, where any user's `ps` shows it; the new process takes it out of its environment at once) and `VTMUX_REATTACH_LOGIN=1` for a client started with `-l` (`argv[0]` can't say so; added 2026-11-10, an older binary ignores it), and the `Hello` extension fields are frozen like the frames, since one build execs the next. Just before each notice the old image sends the client its terminal's teardown, as for a detach (`tty_stop_tty`: alternate screen left, title popped, mouse, bracketed paste, focus reports, keypad and extended keys off); the client writes it out and gives the terminal its termios back before the exec (a few milliseconds in which a typed key echoes; the redraw covers it), so a client that does not come back (its exec fails, the new binary can't re-attach, its token is refused) leaves the terminal as a detach does and says why. It stops reading the socket at the notice, so input it sent before reaches the new image on the old connection. Its terminal is started again as after `MSG_WAKEUP` (`tty_start_tty`), not queried again: its features are in its record, and so is where its queries stand (which are answered, the start timer's time left), which the re-attach keeps. The title the terminal showed from the client's output (`set-titles`, or an OSC 0/2 a pane passed through), which the teardown popped, is given again. A re-attach is let in as the access list says at that moment (another user's connection is refused; a peer made read-only since gets a read-only client). A client told and not back within 10 s (counted in the new image from its start, not set back to the snapshot's time as carried timers are, since the notice goes out after the snapshot), or whose process has exited after its old connection closed, is given up on: detached with the same message, or lost if its old connection has closed. The image that serves holds the requester's answer until every told client has re-attached or been given up on, and names each one given up on in it as a warning (also in `show-messages`). Known limit: an upgrade onto a binary from before this (a downgrade) sends notices that binary can't act on, so its attached clients exit, their terminals restored and named in the requester's answer (the sessions are unharmed). (Revised 2026-11-07 after review_lu_client_reexec, `medium_reexec_teardown`.) Also (found by `oracle replay --upgrade-every`, `lu_upgrade_tests`): a client locked at the upgrade (its `lock-command` running) can't act on its notice until it is back, so it is given up on after the 10 s.

**Ids and observable state.** The server keeps its pid, socket path and inode, session/window/pane/client ids and every option. `#{pid}`, `#{start_time}`, `#{socket_path}` and `#{version}` are unchanged, except that `#{version}`/`-V` report the new binary's version: that is the point.

### Persistence (phase 3)

**Removed 2026-11-12 (M5): restoring is tmux-resurrect's job.** Kept as written when it was removed.

**Writing.** With `vtmux-persist` set to `layout` or `full`, the server writes a checkpoint on clean shutdown and every 60 s when something changed (decision 16). A checkpoint encodes the snapshot as decision 17 trims it (pane terminal state, titles and paste buffers only for `full`; never the message log, environment or prompt history), writes every history page not already in `chunks/` (named by content hash, compressed), writes `manifest.tmp`, flushes it to stable storage, renames `manifest` to `manifest.prev` and `manifest.tmp` to `manifest`, then deletes chunks no manifest references (decision 20). Setting `vtmux-persist` from `full` to `layout` at run time writes a `layout` checkpoint at the next loop turn, changed or not, with `manifest.prev` made a copy of it (replaced before `manifest`, so a crash between the two still reads the old checkpoint with every chunk it names) and the chunks no manifest names deleted: the full checkpoints' screens and history must not stay in `manifest.prev` and `chunks/` until the next change (revised 2026-11-09, `low_restore_refusal_visible`). The loop never waits for the lock for it: refused, it is tried again as a periodic checkpoint is, every 2 ms for 50 ms, then said once in `show-messages` and tried at the next interval (2026-11-12, panel_fix_reap: the wait held the loop up to 50 ms). Nothing on disk is taken on trust: a chunk already in `chunks/` is named by a new manifest, and `manifest` renamed to `manifest.prev` without reading it through, only when this process wrote it or read it back and found it to check (a restore counts what it read); else it is read back first, a chunk per piece of a periodic checkpoint's 5 ms steps, a chunk that does not check is written again from the page, and a `manifest` that does not read over a `manifest.prev` that does is replaced, `manifest.prev` kept. So the read-back at the first checkpoint of a process (a live upgrade's image knows nothing of the directory) holds no loop turn much past its step: 330-360 ms in one turn at 20 panes x 40k lines before, at most 10 ms a turn after; the export that starts every `full` checkpoint (1.3 s there) is apart (revised 2026-11-10, `panel_g2_persist`). The directory is `$XDG_STATE_HOME/vtmux/<socket-name>-<hash>/` (default `~/.local/state`), created mode 0700, files 0600, locked by the server writing it. `lock` is never unlinked: a server may have it open, about to take it, and would then hold a lock on a file the next server does not see, both writing the directory. So the test tool that sweeps dead test servers' directories (`cargo xtask reap`) empties one only while it holds the lock exclusive (taken without waiting, its socket asked again under it, and held only while that one directory is emptied, far short of the 50 ms a restore waits; the socket scan comes first, and a directory it keeps is never locked) and leaves `lock` behind, so the emptied directory stays, holding only that file. Which servers run it asks the kernel, never a command line (which does not say: `-L rvpath/../default` is `default`'s socket, a server with neither `-L` nor `-S` takes `$TMUX`'s, macOS's `ps` joins a value with a space): the sockets held open now (Linux `/proc/net/unix` and `/proc/<pid>/fd`, macOS `lsof -U`), each naming the directory its server would (the name and hash of its absolute path, `..` kept). It keeps a directory such a socket names, one changed within `--min-age`, and every one when the sockets cannot be listed; it kills only old orphans holding a test socket, a real path `.../tmux-<uid>/<label>` or `vtmux-<uid>` with a test label, or an oracle run's (2026-11-12, panel_fix_reap; 2026-11-11, final_fix_reap).

**Restoring.** A server starting with `vtmux-persist` not `off` (the option is read from the config before the first session is created) and a readable `manifest` (else `manifest.prev`) restores it: sessions, windows, layout, options, and (for `full`) buffers. Every pane comes back dead (`#{pane_dead}` 1, exit status unknown) showing its saved screen and history (for `full`) or empty (for `layout`), with `remain-on-exit`'s dead-pane line. `respawn-pane` (or `respawn-window`) restarts the pane's saved start command in its saved cwd. A config that creates sessions (`new-session` in `.tmux.conf`) runs after the restore; a name collision keeps the restored session and reports the config error as tmux would for a duplicate.

How (`lu_persist_restore`, `crates/vtmux-server/src/server/restore.rs`):

- **The setting.** The config's own `set-option` commands for `vtmux-persist` and the global `vtmux-persist-drop` are read before it runs: each config file parsed as the startup config is (`%if` over the empty server), files it sources not followed. A config setting `vtmux-persist off` gets no restore; a config that does not set it leaves it to the checkpoint's value (a runtime `set -s vtmux-persist`), as decision 27 has runtime settings survive unless the config sets them. Turning it off at run time therefore records `off` there: once a loop turn has seen it on, the server takes the lock and rewrites `manifest` and `manifest.prev` with the option `off`, nothing else changed (pages by name, `chunks/` kept), at the next loop turn or at the shutdown in the same command line; a newer binary's or a refused checkpoint is left alone as always, and so is a file that does not decode. The next start restores nothing unless its config turns the option on, and the files stay until the user removes them (the non-goal below); turned on again, the server checkpoints as usual (2026-11-11, `final_fix_upgcheck`: the checkpoint still said `full`, so the next start restored it; removing the manifests would have deleted the user's files).
- **The check.** `manifest`, else `manifest.prev`: the first that decodes, is a checkpoint and passes the dry run a live upgrade uses (`<own binary> --vtmux-check-snapshot <fd>` in a child process, which rebuilds the whole server from it) is imported, so a checkpoint that would crash the rebuild costs a child, not the server. A copy mode holding a page that does not check (its chunk missing or corrupt, or past the reader's limits, as every vtmux before 8c94c6e checkpointed a copy mode over more than 65536 rows) is left out and the rest restored, the pane's own screen and history with it, as a live upgrade's last resort leaves it out, and `show-messages` names it (2026-11-08, `lu_switchback_last_resort`); a pane's own page that does not check still fails the file. One that fails leaves a fresh server, with why in `show-messages` and, when the server then has no session for the client that started it (`start-server`, `attach`: the server exits at once under `exit-empty`, and its message log with it), on that client's stderr as the same line, once, with exit status 1 where its command would have succeeded (`attach` keeps tmux's `no sessions` first; a command that makes a session says nothing; revised 2026-11-09, `low_restore_refusal_visible`); a newer binary's checkpoint (below) is told the same way; its files are kept, and the server writes no checkpoint while `manifest` or `manifest.prev` is still there. The `manifest.prev` fallback is for a `manifest` that is corrupt or truncated in a format this binary reads; once restored from it the server checkpoints as usual. A newer binary's checkpoint is left alone instead (decision 6: an older binary refuses it and must not destroy it; revised 2026-11-07 after review_lu_persist_restore, orchestrator): when `manifest` or `manifest.prev` is of a newer format, or requires a feature this binary lacks, nothing is restored (not from the other file either: restoring `manifest.prev` and checkpointing rotated the newer `manifest` away), the lock is not taken, nothing is written to the directory for the server's lifetime (even if the files go or `vtmux-persist` is turned on later), and `show-messages` says why. A server checks the same before it first writes to the directory, so one that did not restore (its config set `vtmux-persist off`) or that a live upgrade started leaves it alone too. A live upgrade carries what the start found (`persist_hold` in the snapshot's server record), so the new image keeps a refused checkpoint as the old one did (revised 2026-11-08 after audit_persist_restore: the new image wrote over a corrupt checkpoint the old one had kept).
- **What changes on import.** The server is the new one (pid, start time, socket, config files, the starting client's environment). Every pane is dead: no pid, tty or `pipe-pane`; a pane that was alive has status unknown (`#{pane_dead_status}` and `#{pane_dead_signal}` empty) and died at the restore; one already dead keeps its status and time. Each shows `remain-on-exit-format`'s dead line, whatever `remain-on-exit` says (a pane that had a process gets it, or the Enter hint, drawn over its last row instead of written into it, *Respawning a restored pane*), drawn once as tmux draws it (server-fn.c `server_destroy_pane`, `PANE_STATUSDRAWN`): a pane alive in the checkpoint gets it at the restore; one already dead in a `full` checkpoint shows the line its saved screen holds and gets none again (a `layout` checkpoint keeps no screen, so it is drawn again). On a restored screen whose last row is blank the line goes on that row without tmux's scroll, so the saved rows stay where they were and none goes into history (revised 2026-11-08 after medium_persist_full_drops_line: a `cat -` pane with three lines typed came back with its first row scrolled off the screen, and each restart of the restored server scrolled once more and stacked another line); a last row with output scrolls up into history first, as tmux's does. With tmux's default format, which puts a status or a signal before the comma, a pane of unknown status reads `Pane is dead (, <time>)`: the formats keep tmux's meaning (a number or nothing) rather than carry a made-up status, and a config wanting another line sets the format, e.g. `set -g remain-on-exit-format 'Pane is dead (#{?#{!=:#{pane_dead_status},},status #{pane_dead_status},#{?#{!=:#{pane_dead_signal},},signal #{pane_dead_signal},restored}}, #{t:pane_dead_time})'`. A `layout` checkpoint keeps no titles, so each pane gets a new pane's (the host name). Ids and id counters are the checkpoint's. The config runs when the first client says hello, as at any start.
- **The config on top.** The config runs on the restored server as on a fresh one: the first time it sets an option or hook (in any tree, by `set-option`, `set-window-option` or `set-hook`, from the file, a file it sources or a plugin's `tmux set` while it runs), that starts from the option's default (a local one unset), so its value replaces the saved one, its `-a` appends to the default once rather than once more on every restart, and its `-o` is not refused by its own earlier value; options it does not set keep their saved, runtime values (revised 2026-11-08 after audit_persist_restore: each restart added another `terminal-features` item from `set -as`, another command to a `set-hook -ga` hook, and `already set` for `set -go`).
- **`vtmux-persist-drop`.** A session's own value drops the matching user options of the session, its windows and their panes; the global value (the config's when it sets it, else the checkpoint's) applies to the sessions without one, and to the server and global trees. A window linked into several sessions goes by all of them.
- **Full.** A `full` checkpoint's screens and history (rows in vtmux's own format) come back through `snapshot::restore_term`, cell for cell, cursor included, with the titles and the buffers.

**Respawning a restored pane** (decisions 31 and 32, `restore_ux`; revised before building after a refuter's review, 12 findings). **Removed 2026-11-12 (M5): restoring is tmux-resurrect's job.**

- **Provenance.** A pane carries `restored_from`: none, or the time of the checkpoint it came from. A cold restore sets it, to that checkpoint's write time, on every pane that had a process in the checkpoint; a pane already dead there, or one never given a process, stays an ordinary dead pane. A later import (a live upgrade, or a checkpoint written while the pane still waited) keeps it as saved, so the second restart after a reboot still knows. Respawning or killing the pane clears it; a respawn that fails to spawn keeps it, with the screen and no second marker, and one whose program exits at once gives it back (*A restart that does not run*). It is an ignorable snapshot field (SNAPSHOT RULE): a binary that does not know it reads an ordinary dead pane, and a checkpoint that binary writes has lost it for good. A checkpoint writes a waiting pane with no dead time and no status, as a pane alive at the checkpoint (a cold restore drops a status an earlier build wrote: a failed restart's is the server's that tried it), so such a binary's cold restore draws its dead line as for one (3.8.0-beta.2 draws none on a pane with a dead time and a saved screen, whose line the screen held then); this build dates its death at each restore, as for any pane that ran (2026-11-11, `panel_fix_restore`). Known limit: a live upgrade onto such a binary (a downgrade) carries the dead time as it is, so that binary shows the saved screen with no dead line until the pane is respawned; writing the line into the grid for it would need the bottom row carried beside, for one cosmetic line on a downgrade.
- **The hint.** A restored pane's status text is drawn over its bottom row by the renderer, never written into its grid, whatever the option: `Restored <time>: Enter restarts <command>` while `vtmux-persist-respawn` is `key` or `auto` (on a pane too narrow for `Enter restarts` after the time, the time goes, then a failure's text; the command is clipped), `remain-on-exit-format`'s dead line while it is `off` (nothing for an empty format, as tmux's `server_destroy_pane` draws nothing), switching when the option changes. `capture-pane`, copy mode, reflow on resize and checkpoints never see it. A dead line an older vtmux wrote into a checkpointed screen is saved content and stays. Ordinary dead panes keep tmux's dead line in the grid.
- **Respawning one** (`respawn-pane`, with or without `-k`, a new command, `-c` or `-e`; the key; `auto`). In order: if the alternate screen is active, copy its visible rows; the resets an ordinary respawn does (parser, modes, attributes, scroll region, margins, origin and insert mode, charsets, tab stops, synchronized output, protocol grants, saved cursors, leaving the alternate screen and resizing the main one to the pane, as tmux's `screen_alternate_off`) but not clearing the grid and not homing the cursor; then the copied rows, if any, appended below the main screen's last occupied row (scrolling it into history as needed): blank lines are fed for them, then the rows are put over those lines cell for cell through the state export and import a live upgrade uses (`PaneTerm::copy_rows`, `put_rows`), so text, widths, styles (an erase's coloured blanks too), links with their ids, the line-drawing mark, tabs and the row flags are what they were; the first copied row continues nothing and the last is hard, and a link without an id becomes a new one of the main screen (revised 2026-11-12, `final_fix_restore`: replayed as `capture-pane -e -J` text they lost DEC line drawing, coloured erased cells, a link going on past a line end and doubled an id's backslash); then the marker row, default attributes, hard (not wrapped), clipped to the pane width, on the row below the last occupied row (a cell is occupied when it was written: text, an explicit space, a style or a link), or on the top row of a blank screen; then the cursor at column 0 of the next row, scrolling at the bottom; then the spawn. History keeps what `history-limit` allows. `respawn-pane -E` (no process) keeps the provenance and writes nothing. Only the screen at the respawn is promised: the new program may clear it.
- **A restart that does not run** (2026-11-11, `panel_fix_restore`, after the M4 panel showed a restored pane's screen and history destroyed by Enter into a binary gone since the checkpoint; revised 2026-11-12, `final_fix_restore`). The program a restored pane was respawned into (by any of the three) that exits before any input was written to it (a key, a paste, a mouse report, `send-keys`, `paste-buffer`, `pipe-pane -I`; not a terminal reply or a focus report the program asked for, and not the Enter that respawned it, which is consumed) does not close the pane or get tmux's dead line, whatever `remain-on-exit` says: the pane goes back to waiting as restored from the same checkpoint, dead with that exit's status (`#{pane_dead_status}`), `pane-died` fired as for a pane `remain-on-exit` keeps, its screen as it is then (the old screen, the marker, what the program wrote) and its history kept, and the hint reads `Restored <time>: restart failed (status N); Enter restarts <command>` (`signal N` for a signal, `exited (status 0)` for a success). Enter or `respawn-pane` tries again, writing another marker. Once input has been written to it, the program exits as any pane's does. The guard is an ignorable snapshot field (`restart_from`): a live upgrade keeps it, a build before closes the pane on that exit as on any; a cold restore drops it (the pane is restored again). Why input and not a time or the status: a missing program and a failing one look alike to the server (both exit with a status after `exec`); a time (the first rule: within 2 s of the spawn) was taken when the server handled the exit, so a stalled loop, a `pipe-pane` slow to drain or late reaping turned a fast failure into an ordinary exit and lost the screen, and no portable call gives a child's own run time; a program nobody has typed into has given the user nothing the saved screen did not, while closing the pane loses that screen for good. A pane kept that tmux would close (a command restarted with `respawn-pane` that runs to its end untouched) costs a `kill-pane`.
- **`respawn-window`** keeps tmux's semantics (spawn.c `spawn_window`): every pane but the first is removed with its screen; the first, if restored, respawns as above at its new size. A restored pane elsewhere does not make the first one restored.
- **The key.** Enter is a respawn only as a client key, last: after overlays, prompts and the key tables (a binding on Enter wins, copy mode keeps its Enter), when the active pane is restored and has no mode open, from a client that is not read-only. It is consumed: not written to the new process, not sent to synchronized panes, and a synchronized peer is never respawned by it. `send-keys Enter`, `send-keys -l` and `-H`, `paste-buffer` and pasted bytes never respawn (scripts that send keys to dead panes keep doing nothing); `send-keys -K` acts as a client key. tmux's `remain-on-exit key` and `failed-key` (server-client.c `server_client_handle_dead_key`: any key closes the dead pane) are bypassed for a restored pane while the option is `key` or `auto`, and apply again once it has been respawned; with `off`, and for every other pane, they apply as in tmux.
- **`auto`.** One pass, only after a cold restore from a checkpoint (never after a live upgrade or when the option is set later), when the startup config's queue has finished (not background plugin jobs), before the starting client's command runs. It takes each pane once (a window linked into several sessions counts once), in session, window and pane order, and respawns it when it is still restored and dead and its saved command is empty (it ran the pane's saved shell; a nonempty `default-command` is saved as the command and does not count). Panes the config respawned, killed or created are skipped by that check. A pane that fails to spawn stays restored and is named in `show-messages`. The saved shell and cwd are used (a missing cwd falls back to home, then `/`, as tmux's `spawn_pane`), and the environment is built as for any respawn (environ.c `environ_for_session`: the global environment after the config, then the session's), the session being the first in that order that holds the window; there is no client environment.
- **Edge:** `respawn-pane` and `respawn-window` grammar, exit codes and hooks (`pane-died` is not run again) are unchanged; every pane that is not restored behaves as in tmux whatever the option says. `vtmux-persist off` stops restores and checkpoints; a pane restored before it was set keeps its provenance.

**Tools that read session state** (tsesh, murmur): see decisions 29 and 30 (Removed 2026-11-12 (M5): restoring is tmux-resurrect's job.). During a live upgrade nothing changes for them: the listening socket stays open across the exec, so a command arriving mid-upgrade waits in the kernel's accept queue.

**Non-goals here:** no restore of anything after the server exits (removed 2026-11-12, M5: restoring is tmux-resurrect's job; this read: no automatic relaunch of anything but shells, and that only with `vtmux-persist-respawn auto`, no restore of processes, no cross-machine restore, no restore when the option is off).

## Tests

- **Round trip (unit):** encode, decode and compare every snapshot record type; decode every older version kept as a golden file under `crates/vtmux-snapshot/tests/golden/` (one per format version; never edited after release).
- **Terminal state (unit + property):** for random terminal programs (escape-sequence fuzzer seeds), export, import into a fresh terminal and compare `capture-pane -e -S -`, cursor, modes and row flags exactly.
- **Oracle step `upgrade`:** the oracle harness gains a step that runs `vtmux-upgrade -b <same binary>` on the vtmux side only (the reference tmux skips it) and then continues; scenarios that already pass must pass with an `upgrade` step inserted at any point. A replay mode that inserts an upgrade after every Nth step of every scenario runs in CI. How (`lu_upgrade_tests`, orchestrator's builder): the step asks over the frozen `UpgradeRequest` (as `vtmux-upgrade -b` does from a client of another version), which leaves no `command:` line in `show-messages`, then waits for every attached client to re-attach and show again the screen it showed before (its redraw follows the restart frame's acknowledgement, so a quiet time alone can end first under load: `flake_replay_upgrade_screen_blank`, 2026-11-11); `replay --upgrade-every 3` runs in `scripts/check.sh`. "Any point" means any point where the upgrade changes nothing a scenario observes by design: the server's test hook `VTMUX_TEST_UPGRADE_STRICT` (never in the global environment) refuses at once, and the runner tries a step later, where an upgrade would wait for work in flight (a pane's `tmux wait-for`, a job) or change what a client sees (a mode, prompt, menu or editor popup it closes, a status message, whose frozen screen is redrawn as it is now and whose timer runs on, a key held for `escape-time`, a mouse drag or a click waiting for a second, a locked or suspended client). Scenarios that observe what the re-attach redraws as any attach does (cached border styles, synchronized output, a lazily redrawn status line), a `#()` job's fresh output, or a known bug are listed with why in `oracle/upgrade-every-skip.toml` and replayed without inserted upgrades.
- **Upgrade under load (integration):** 10 panes streaming output, one PTY client, two control clients reading `%output`: upgrade; no pane process restarted (pids equal), no output byte lost or duplicated in the control clients' streams, the PTY client's rendered screen equal to a fresh attach, time to redraw recorded (target < 1 s, decision 13).
- **Failure paths:** a binary that fails the dry run (garbage file); a binary that fails after exec (test hook makes `--vtmux-resume` fail) and switches back; an old client that ignores `UpgradeNotice`; a pending `run-shell` refusal.
- **Persistence:** **Removed 2026-11-12 (M5): restoring is tmux-resurrect's job.** Checkpoint, `kill -9` the server, start it: sessions, layout and dead panes with screens match the checkpoint; crash in the middle of writing (test hook between chunk writes and the manifest rename) restores the previous manifest; a restored pane respawned (command, key, `auto`) keeps its screen, the alternate one included, above the marker and the new prompt, also after a resize; only empty-command panes respawn under `auto`, after the config; `send-keys Enter` and synchronized peers never respawn one; `remain-on-exit key` does not close a restored pane under `key`; a non-restored dead pane respawns as tmux's; the provenance survives a live upgrade and a second restart; `layout` writes no user content (grep the directory for a pane's text, environment, `send-keys` and `set-buffer` text, a copied buffer, prompt history and a search: none; the message log, environment and prompt history in neither mode); a polled idle server writes nothing; two sockets of one name keep two directories; a locked directory is not written.
- **Bench:** `scripts/bench.py upgrade`: time from request to redraw and snapshot size at 1/10 panes x 10k/100k lines, recorded in `docs/PERFORMANCE.md`.

## Scope

In: everything above, Linux and macOS.

Out: automatic upgrade on a newer client (decision 3, later option); any restore after the server exits (removed 2026-11-12, M5: tmux-resurrect's job), so restoring processes, relaunching commands, cross-machine or cross-user restore; a JSON dump command (later, for debugging); Windows.

## Open questions

- ~~Whether tree modes, menus, prompts and popups survive an upgrade or are closed by it~~ Decided in phase 1 (`lu_model_snapshot`, `crates/vtmux-server/src/server/snapshot.rs`): **carried** are copy mode (frozen grid with line times, OSC 133 marks and hyperlinks, view, selection, search, jump, mark) and clock mode, and popups (geometry, title, styles, close rules, the pty and its process; the terminal comes with pane terminal state). **Closed** are view mode (its backing terminal is pane terminal state; `PaneMode::View` is kept in the format for when that is carried), the tree modes (`choose-tree`, `choose-buffer`, `choose-client`, `customize-mode`, `switch-mode`), `display-panes`, every prompt (status line, `command-prompt -P` pane prompts, a mode's own prompt), menus, and a popup editing a buffer or option through an editor: they hold callbacks into commands in flight and re-opening them is cheap. A closed mode leaves the modes under it on the pane's stack. The edit in an editor popup (`e` in `choose-buffer` or `customize-mode`) is dropped with it, by design, as when its mode ends first (spawn.c `spawn_cancel_editor`): the popup is not carried, and its 0600 `/tmp/tmux.XXXXXXXX` file is removed by the old image just before the `execve`, since no destructor runs across it (`Popup::discard_editor_file`; not at the snapshot's export, which runs for every dry run and persistence checkpoint while the server serves on; `an_editor_open_across_an_upgrade_leaves_no_temp_file`). If the `execve` fails the popup stays and its edit is lost, since the file is gone (the editor may write it again, and the mode reads it when the editor exits 0).
- The real upgrade time at 10 panes x 100k lines: the first bench sets whether a raw-page fast path is needed (decision 11). Measured 2026-11-07 (`bench.py upgrade`, release, `lu_upgrade_tests`; docs/PERFORMANCE.md, *Live upgrade*): with the history compressed (Ghostty pages, decision 23) 1.7 s from request to redraw, 0.2 s at 1 x 100k or 10 x 10k; with it not yet compressed about 1 s per 100k lines in all, and at 10 x 100k the dry run passes its 3 s limit, so the upgrade is refused. ~~Decision 13's 1 s is not met at its size: open.~~ Met after `lu_upgrade_perf` (same day): 0.6 s compressed, 0.75 s not yet compressed, RSS after the upgrade what it was before; the blob checksum (Zig's `XxHash3`, 250 MB/s) was most of the 1.7 s, and history that was not compressed is compressed first instead of going as rows (decision 23). Still about 1 s per 100k lines (10 s at 10 x 100k) onto a binary of another patch stack, where history must go as rows; no longer refused for its size (step 4's limit grows with it).
